# PU Workspace

MVP безопасного органайзера проектных документов в Google Drive.

## Гарантия первого релиза

Органайзер не изменяет исходную папку. Рабочий цикл всегда начинается с
создания отдельной копии, а перемещение и переименование допускаются только
внутри её дерева:

`выбор папки → безопасная копия → анализ → предложение → подтверждение → применение → журнал → откат`

Точные дубли и предполагаемые версии не удаляются. Неоднозначные и особые
случаи требуют явной ручной проверки.

Доступ к проектам изолирован членством и ролями `viewer`, `member`, `editor`,
`manager`, `owner`. Проверка выполняется не только для списка проектов, но и
для вложенных session, proposal, action, document, history и Drive-ресурсов.
Глобальный аудит и правила доступны только администратору. Истёкшие bearer-
сессии удаляются при старте приложения и при выдаче новой сессии.

## Запуск

1. Выполните `powershell -ExecutionPolicy Bypass -File scripts/setup-local.ps1`.
   Скрипт создаст `.env` со случайными локальными секретами и не перезапишет
   существующий файл без явно переданного `-Force`.
2. Заполните в `.env` Google OAuth credentials.
   Создайте ключ токенов командой
   `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.
   Также задайте случайный `BOOTSTRAP_TOKEN` длиной не менее 24 символов.
   Он используется только для создания первого администратора.
3. В Google Cloud Console добавьте redirect URI
   `http://localhost:3000/projects/google/callback`.
4. Запустите `docker compose up --build`.
5. Откройте `http://localhost:3000` и раскройте «Первый запуск» для создания
   администратора с `BOOTSTRAP_TOKEN` из `.env`.

Перед стартом backend контейнер применяет версионируемые миграции Alembic.
Для локального запуска из каталога `backend` выполните
`alembic -c alembic.ini upgrade head`.

Если база ранее создавалась старой версией через `create_all`, сначала
сравните её схему с начальной миграцией и только после подтверждения выполните
`alembic -c alembic.ini stamp head`; автоматическое stamp намеренно запрещено.

## Проверки

Установите зависимости из `backend/requirements.txt`, затем из каталога
`backend` выполните:

```text
python -m pytest -q
```

По умолчанию приложение ожидает PostgreSQL по адресу из `DATABASE_URL`; hostname
`db` доступен только внутри Docker Compose. Для локального интеграционного
прогона сначала запустите `docker compose up -d db`, задайте отдельную тестовую
базу с именем, оканчивающимся на `_test`, примените миграции и включите тесты:

```text
DATABASE_URL=postgresql://pu_test:password@127.0.0.1:5432/pu_workspace_test
PU_TEST_POSTGRES=1
alembic -c alembic.ini upgrade head
python -m pytest -q
```

CI создаёт чистый PostgreSQL 16, применяет все Alembic-миграции, запускает
полный `pytest`, `pnpm run check` и `pnpm run build`, после чего сохраняет три
лога проверки как artifact конкретного commit SHA.

Для интерфейса из каталога `frontend`:

```text
pnpm run check
pnpm run build
```

Backend-тесты фиксируют консервативное именование, обработку дублей/версий,
права доступа, управленческие контуры и жёсткую границу, запрещающую изменение
объектов вне безопасной копии. Frontend-проверки включают TypeScript и
production-сборку.

Перед демонстрацией покупателю используйте read-only preflight и сценарий из
[`docs/DEMO_RUNBOOK_RU.md`](docs/DEMO_RUNBOOK_RU.md).

## Безопасность сессии и Telegram

Новый интерфейс использует серверную сессию в `HttpOnly`, `SameSite=Strict` cookie. Изменяющие запросы дополнительно проверяются CSRF-токеном; bearer-токен остаётся совместимым только для API-клиентов и не хранится фронтендом в `sessionStorage`.

Порядок ротации скомпрометированного Telegram-токена описан в `docs/TELEGRAM_TOKEN_ROTATION_RUNBOOK_RU.md`.

## MVP3 — управленческий контур

Новый интерфейс `/new/` содержит реестры обязательств, задач, рисков и
решений, протоколы совещаний, центр уведомлений и сводный экран «Требует
внимания». Протокол совещания после явного сохранения анализируется тем же
ядром, что документы и сообщения: выделенные поручения, риски и решения имеют
проверяемый источник. Внешние Google Tasks и Calendar по-прежнему создаются
только после отдельного подтверждения пользователя.

Уведомления формируются идемпотентно по ближайшим и просроченным срокам,
открытым рискам и ожидающим решениям. Обновление статуса обязательства и
протокола записывается в аудит.

## MVP4 — исполнение и финансы

Раздел `/new/` «Исполнение и финансы» объединяет версии ГПР и план/факт
работ, бюджет проекта, календарь ДДС, закупки и поставки, акты и закрывающие
документы. Сводка рассчитывает отклонение бюджета, прогноз остатка,
потенциальный кассовый разрыв, отстающие работы и просроченные поставки.

Новые управленческие данные сначала создаются со статусом предложения.
Утверждение baseline, бюджета, платежа, заказа или акта выполняется отдельным
действием пользователя и записывается в аудит. Исходные документы и папки
Google Drive этот контур не изменяет.

## Текущее ограничение MVP

Scan-задания выполняются локальным пулом и восстанавливаются после рестарта:
при наличии безопасной копии повторное копирование не запускается. Текущая
реализация рассчитана на один backend-процесс; перед горизонтальным
масштабированием нужен внешний broker и распределённые leases.

## MVP6–7 — документный контроль и AI Secretary

MVP6 ранжирует проанализированные ГПР, сметы, ДДС, счета и акты и предлагает
связать их с договорным и финансовым контуром. Уверенность и причины видны
пользователю; создание записи требует проверки и не изменяет оригинал.

MVP7 поддерживает ежемесячные регламенты AI Secretary: в назначенный день
создаются внутренняя задача и черновик письма. Пользователь видит результат
запуска и отдельно подтверждает внешнюю отправку или финансовый факт.
