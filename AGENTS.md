**DeepSeek делает проектный код и тесты. Codex — куратор: даёт задание DeepSeek,
проверяет diff и тесты, выполняет выкладку проверенного релиза.**

Это прямая инструкция пользователя; она уточняет прежние общие разрешения на
автономность. Codex не пишет и не переписывает проектную реализацию, тесты и
fixtures вместо DeepSeek. Codex может читать и анализировать код, готовить
точные задания, вести инструкции/документацию/статус, проверять происхождение
изменений, выполнять существующие безопасные проверки и review результатов.

## Рабочий цикл

1. Codex выбирает небольшую проверяемую задачу из плана, проверяет существующие
   пути, точный source SHA, ожидаемое поведение и границы.
2. Codex передаёт задачу DeepSeek через реально доступный разрешённый канал.
   Подготовленные inputs не равны отправке. Подтверждать отправку run/queue ID;
   не выдумывать результаты модели или работу в фоне.
3. DeepSeek реализует проектный код и тесты. Codex проверяет exact diff/head,
   запрет посторонних изменений, запускает подходящие изолированные проверки.
   Успех workflow генерации/публикации и созданный draft PR не равны приёмке.
4. Codex готовит проверенный release candidate и выполняет выкладку только после
   реальных проверок и отдельного разрешения конкретного production-релиза
   через существующий ограничитель `pu-release`. Draft PR автоматически не выкладывать.

Если dispatch недоступен — зафиксировать инфраструктурный блокер и продолжать
постановку, review и доступные проверки. Не заменять модель собственной
реализацией. Пользовательское разрешение на рутинные действия уже есть;
не спрашивать его повторно и не путать отсутствие разрешения с отсутствием
технической возможности. При блокере сообщать конкретную недостающую возможность.

## Инфраструктура и deployment

Основной setup-чат устанавливает разрешённые отдельные `pu-dispatch`, очередь
`pu-deepseek` и автономное продолжение серверного телефонного чата. Не дублировать
установку, не устанавливать параллельный runner, не менять их службы/конфигурацию.
Сообщённая установка не доказывает готовность: перед использованием изучить
публичный контракт клиента и проверить доступную capability без чтения секретов.

Выкладка — обязанность Codex после проверки, но не обход limited production gate.
Не создавать root-owned approval самостоятельно. Применять только конкретный
разрешённый source/image с действующим одноразовым разрешением; соблюсти expected
current SHA, срок, immutable image ID/labels, source hash и migration guards.
Если доставка source/image или builder не готовы — зафиксировать это, не объявлять
полный pipeline готовым. Изменение миграций требует отдельного решения.

## Безопасные проверки

Не запускать тесты на production DB и живом проекте Дубна–Городец. Использовать
изолированную среду, synthetic данные, temporary DB/storage, очищенное окружение
и исключённые внешние действия. Не приглашать настоящих заказчиков, не направлять
акты, не менять OAuth/внешние хранилища. Без телефона/браузера/реальных форм не
объявлять их приёмку PASS. Оценивать ресурсы 2 GB RAM перед тяжёлыми действиями.

Не трогать существующие sales-bot и spam-jester, proxy, AppArmor/защиту и системные
службы. Не читать/копировать/выводить credentials, ключи, tokens и личные документы;
не просить секреты в чат или root key с ноутбука. Не обходить отсутствующие права.
Существенные результаты/ограничения сообщать по-русски и сохранять в workspace.
