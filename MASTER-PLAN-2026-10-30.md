## Цель и оценки

Продукт для подрядчика: работа на объекте, фактические объёмы, документы и согласование с заказчиком в одной цепочке. КС формируются ТОЛЬКО из факта журнала, цены из сметы, превышение доступного сметного объёма блокируется.

Предварительная оценка: 60 рабочих дней (около 12 недель), плюс 2–3 недели календарного резерва на реальные файлы, интеграции и приёмку. Первый комплект «смета → журнал → КС → заказчик» — ориентир 3–4 недели. Это оценки, не гарантия. После первых трёх рабочих дней уточнить по фактическим пробелам. Дни относительные: календарная дата старта и календарь праздников не согласованы, не выдумывать дедлайны.

## Этап 0 — 3 дня

Сопоставить согласованный план с checklist 30.10. Для каждого пункта: реализован/проверен/сломан/отсутствует/зависит от данных, с доказательствами. Завершить исправление публикации DeepSeek и проверить небольшой цикл КОДА с тестами/review. Настроить отдельную тестовую БД и синтетические данные. Не считать исключённые при переносе шаблоны отсутствующими в upstream.

Приёмка: объём ясен, проверки воспроизводимы, рутинные действия не требуют копирования команд пользователем.

## Этап 1 — 8 дней

Проверить существующий импорт смет: разделы, позиции, шифры, единицы, объёмы, цены, ошибки строк. Связь журнала с позициями, включая изменение/удаление записей. Факт периода, ранее актированные объёмы, остатки. Повторное формирование, округления, изменение цены и конкурентные действия. Word/Excel КС-2/КС-3, реквизиты и согласованность итогов.

Приёмка: тестовый проект проходит цепочку без переноса объёмов вручную и без двойного учёта. Нужны реальная смета и принимаемые заказчиком формы КС; без них продолжать независимую работу на синтетических данных, не объявлять совместимость реальных форм доказанной.

## Этап 2 — 5 дней

Сначала серверное разграничение, затем UI. Заказчик видит только разрешённый проект, ход работ и направленные документы. Финансы подрядчика, закупки и внутренняя почта недоступны и по прямому API. Приглашение/отзыв доступа, комментарии, согласование/отклонение, история, защита повторного решения по устаревшему акту.

Приёмка: две тестовые учётные записи проходят согласование, чужие данные недоступны. Реальных заказчиков не приглашать без отдельного поручения.

## Этап 3 — 10 дней

Порядок: удобство журнала/замечаний → фото, ответственный, срок, история/закрытие → точка и версия чертежа → offline-очередь с состоянием, повтором и защитой от дублей → минимальный бот (запись, замечание, задачи дня).

Приёмка: запись/замечание создаются без связи и синхронизируются без потерь/дублей. Камера и UX проверяются на реальном телефоне. Существующий sales-bot на сервере не входит автоматически в этот этап; его диагностика отложена, оба существующих бота неприкосновенны.

## Этап 4 — 9 дней

Диадок: получение и сопоставление документов, повторы/ошибки. 1С: один согласованный формат для конкретной конфигурации. API: ограниченные права, отзыв ключей, аудит и документация.

Приёмка: повторная доставка без дублей, наблюдаемые ошибки и безопасный повтор. Подписание/отправка юридически значимых документов — отдельная постановка. Универсальная интеграция со всеми 1С не обещана. API Диадока пока не передан.

## Этап 5 — 8 дней

Недельный PDF-отчёт с фактом, фото, замечаниями и статусом документов. Общие реквизиты, версии шаблонов, обязательные поля. Первые ТРИ новые формы выбрать по проектной потребности; остальные формы исходного roadmap — последующие задачи после проверки движка.

Приёмка: документы открываются, корректно печатаются, данные согласованы; пригодность формы подтверждается приёмкой, а не только созданием файла.

## Этап 6 — 12 дней

Приход материалов, остатки, списание на работы, корректировки и история; разделять физическое движение и финансы счёта. Просмотр/версии/сравнение чертежей. Минимальное самостоятельное подключение компании/первого проекта.

Приёмка: повторы не удваивают приход, корректировка сохраняет историю, замечания сохраняют связь с версией. Первоначально сравнение PDF/изображений; полноценный CAD/BIM отдельно. Биллинг и окончательные тарифы отдельно, без изменения реальных платежей/оферт.

## Этап 7 — 5 дней

Checklist 30.10 на изолированном стенде, мобильные сценарии/права, backup и восстановление тестового экземпляра, критичные дефекты, известные ограничения, инструкции/выпуск/откат.

Приёмка: нет известных критичных дефектов согласованного объёма, ограничения перечислены; production-выкладка только по отдельному решению пользователя.

## Автономная работа и границы

Codex ведёт план, выбирает ограниченную задачу и проверяет результат. DeepSeek получает конкретные файлы/ожидаемое поведение/критерии. Отдельная ветка, review и подходящие тесты. Созданный PR не равен выполненной задаче. Статус в серверных файлах и телефонном чате. Пользователю — существенные результаты, блокеры, необходимые решения и подтверждение production-изменений, не каждая рутинная команда.

Не объявлять непрерывное планирование и самостоятельный dispatch DeepSeek настроенными без проверки. DeepSeek API и draft PR в GitHub реально проверены запуском 41078234904 (PR364). PR363 исправляет publisher; его merge/CI проверять по актуальным данным. Серверный GitHub-доступ для dispatch не предоставлялся. Ключ только в GitHub Secrets, не читать/переносить его. Существующий workflow не заменяет тесты/review; production deploy и auto-merge не включать.

Реальный проект Дубна–Городец не менять для тестов; production DB недоступна для тестов; внешние хранилища, реальные приглашения/отправки, OAuth, proxy, системные службы не менять. Агент codex-worker без sudo/docker, сервер 2GB RAM; оценивать ресурсы перед тяжёлыми проверками.

Входные данные: сначала смета и КС-2/КС-3; далее кабинет заказчика, конкретная 1С, Диадок и формы ИД. Не просить секреты в чат. Не блокировать независимую работу отсутствием входных данных.
