# ADR: Переоткрытие пилота MVP-5 (V6-07) — bootstrap authority и пересмотр context_confidence

Статус: ADR утверждён владельцем 06.10.2026. Реализация ставится после формального закрытия MVP-4 (V6-00) — по порядку, согласованному владельцем: «сначала MVP-4, потом MVP-5». Утверждение этого ADR не включает AUTO обратно и не разрешает производственные действия — оно разблокирует написание и тестирование кода.

Контекст: пилот MVP-5 (V6-07) закрыт отрицательно 02.10.2026 (`ADR-MVP5-PILOT-CLOSURE-RU.md`, не смержен в main). Возобновление требует выполнения трёх условий из того решения; третье («появилась практическая потребность в автономных действиях») — бизнес-решение владельца, зафиксированное отдельно устным согласием продолжить. Этот ADR закрывает технические условия 1 и 2.

## Условие 2 (context_confidence) — решение

Прочитан код маршрутизатора (`app/api/ai_secretary.py:141-175`, `project_candidate()`) и путь Gmail (`app/api/gmail.py:420-430`). Факты:

- `project_candidate()` уже возвращает **0.95**, если в тексте письма найдено ровно одно совпадение — по названию проекта **или** по номеру договора (`:170-172`).
- При отсутствии совпадения по контенту `gmail.py` **уже проверяет подтверждённый контакт проекта** (`ProjectContact.confirmed=True`, привязан к тому же mail-подключению) и, если найден, **поднимает confidence до 0.95** (`:426-428`).
- Константа **0.55** — случай «ни название, ни номер договора, ни подтверждённый контакт не найдены» (`:175`), а не жёсткий потолок маршрутизатора.

Вывод: во время наблюдения 22-29.09.2026 не было ни одного подтверждённого `ProjectContact` для реальных отправителей проекта №17, и ни одно письмо не содержало явный номер договора/название проекта текстом. Механизм достижения ≥0.9 уже существует — он не был использован, а не отсутствует.

**Решение владельца: Вариант A первым, без кода.** Перед повторным запуском пилота — подтвердить (`ProjectContact.confirmed=True`) реальных отправителей проекта №17 в том же mail-подключении и прогнать проверку: даёт ли это ≥10 писем с confidence ≥0.9 за контрольное окно.

**Эскалация на Вариант B одобрена заранее.** Если Варианта A недостаточно (например контрагенты пишут с разных адресов без устойчивого контакта) — сразу переходим к Варианту B: новый сигнал уверенности (например подтверждённая организация-контрагент целиком, не только личный контакт, либо явная ссылка на документ/вложение, уже привязанный к проекту). Жёсткий пол `minimum_confidence >= 0.9` (`app/pilot_product.py:79,97`) не трогаем — Вариант C отклонён.

## Условие 1 (bootstrap authority) — решение

Факт из кода (`app/core/v54_authority.py:145-162`): единственный способ продлить/переиздать мандат — `change()`, которая сама требует **уже действующего** `authority.manage`. Истёкшая запись этого разрешения не даёт — замкнутый круг. Ни в одном файле кроме моделей не создаётся `AuthorityState(...)`: единственная существующая запись (project 17) была создана разовой ручной операцией при настройке пилота, не воспроизводимым протестированным путём.

**Решение владельца: конструкция `AuthorityBootstrap` одобрена как описана, один admin достаточен (без two-person rule).**

- Отдельная функция/эндпоинт, авторизуется через `require_admin` (глобальный admin-флаг пользователя), **не** через `require_principal`/`change()` — иначе наследует тот же замкнутый круг.
- Создаёт новую строку только если: (а) строки для (project, principal) не существует вовсе, или (б) существующая строка **истекла** (`valid_until <= now`). Активную неистёкшую строку bootstrap не трогает — для неё остаётся обычный `change()`.
- Новый `authority_epoch`: при пересоздании — `(старый epoch) + 1`, при первом создании — `1`.
- Отдельное audit-событие `AUTHORITY_BOOTSTRAPPED` (не `AUTHORITY_CHANGED`) — в журнале различимо «продление штатным владельцем» от «восстановление глобальным admin после истечения».
- `valid_until` новой записи — короткий срок (несколько дней, как у исходного пилота), не длинный мандат.
- **Bootstrap-admin при запуске — владелец лично** (его существующий `is_admin=true` аккаунт, без создания отдельной технической учётки).

## Что этот ADR не разрешает

- Не включает AUTO обратно сам по себе — только разблокирует код.
- Не меняет исходное условие §27.1 и каноническую финансовую цепочку.
- Реализация и тесты — отдельный PR (или несколько), после закрытия MVP-4/V6-00.
- Производственный запуск (реальное выполнение `AuthorityBootstrap` на project 17, реальный повторный пилот) требует отдельного явного действия владельца после кода и тестов — так же, как и для прежнего пилота.

## Обязательные тесты реализации

- Вариант A проверяется прогоном на реальных данных, не юнит-тестом — отдельный шаг перед кодом Варианта B.
- `AuthorityBootstrap`: создание при отсутствии строки; отказ при наличии активной неистёкшей строки (должен идти через `change()`); успешное пересоздание при истёкшей строке с `epoch+1`; отказ для не-admin пользователя; audit-событие `AUTHORITY_BOOTSTRAPPED` с полным набором метаданных, без секретов.
- Если понадобится Вариант B: новый сигнал уверенности покрыт тестом на реальный и синтетический случай, жёсткий пол 0.9 не ослабляется ни для одного другого пути.
