# ADR: V6-05 — доходный бюджет и направление бюджетных строк

Статус: ADR утверждён владельцем 06.10.2026 по итогам пошагового разбора вариантов. Реализация разрешена с учётом ограничений ниже; подтверждение этого ADR не заменяет подтверждения конкретного финансового preview при реализации. Владелец отдельно отметил: при необходимости решения этого документа можно пересмотреть после начала реализации.

Все числовые примеры и названия в этом документе вымышлены. Производственные идентификаторы, суммы и координаты документов остаются вне Git.

## Проблема

`BudgetLine.line_kind` допускает только `legacy_unclassified`, `contract_control`, `analytical_expense` (`dds_article_budget.py:123`, `:396`). Доходной стороны в бюджете нет вообще: договоры `customer` и `revenue_subcontract` в бюджет не попадают, хотя `contract_roles.cash_flow_direction()` уже умеет выводить `inflow` для этих видов договоров. `CashFlowEntry.direction` уже различает `inflow`/`outflow` (`execution_finance.py:291`, `:493`, `:1372`) — факты направление знают, бюджет — нет. Следствие: итоговая маржа проекта посчитана быть не может.

## Что уже есть в коде (факты, зафиксированы на момент ADR)

- `contract_roles.cash_flow_direction(kind)` возвращает `inflow` для `customer`/`revenue_subcontract`, `outflow` для `downstream_subcontract`/`supply`, `None` для `prime_reference`.
- `BudgetLine` не имеет поля `direction`; направление нигде не персистится на уровне бюджета.
- `CashFlowEntry.direction` уже `inflow|outflow` и используется в балансах (`execution_finance.py:1372`).
- Валидатор `dds_article_budget.py` жёстко перечисляет допустимые `line_kind` в двух местах (`:123`, `:396`) — расширение набора значений требует правки обоих.
- Логика «одна аналитическая статья на (contract, currency, period, revision)» (`:388–:409`) написана в предположении, что все аналитические строки расходные.

## Решение владельца

1. **Направление хранится явным полем** `direction: inflow|outflow` на `BudgetLine`, независимо от `contract_id` (а не выводится неявно из `contract_kind` на каждой агрегации). Отклонённые варианты: вывод из `contract_kind` без нового поля (риск смешения доходных/расходных строк в ключе уникальности статьи при смене роли договора); гибрид с ручным override и аудитом (избыточная сложность для текущего объёма задачи).
2. **Вводится отдельная плановая доходная строка бюджета** на договор `customer`/`revenue_subcontract` — не только факт из `CashFlowEntry.direction=inflow`. План и факт по доходу сравниваются симметрично расходу.
3. **Несовпадение direction и роли договора запрещено жёстко (422).** Строка `direction=inflow` на договоре `downstream_subcontract`/`supply` (и наоборот) отклоняется валидатором на создании/обновлении, без preview-предупреждения и без ручного исключения.
4. **Backfill существующих `legacy_unclassified` строк:** `direction=NULL` до ручного разбора, по аналогии с действующим `BUDGET_SCOPE_UNKNOWN`. Ничего не классифицируется автоматически; такие строки исключаются из маржи до подтверждения.
5. **Маржа проекта = `sum(inflow) − sum(outflow)` по подтверждённым бюджетным строкам.** Отдельной сущности для маржи не вводится — это производная метрика бюджета.

## Риск задвоения (почему это не повторяет ошибку ADR-DDS)

ADR-DDS зафиксировал ошибку «контроль договора + аналитическая статья = задвоение». Здесь аналогичный риск — доходная и расходная строка одного договора в одном итоге — закрывается пунктом 3: направление договора и направление строки обязаны совпадать, поэтому у одного договора не может быть одновременно подтверждённой `inflow`- и `outflow`-строки, кроме случая `legacy_unclassified` (`direction=NULL`), который осознанно исключён из итогов до разбора.

## Миграция

Новое поле `direction` на `BudgetLine`, nullable на старте (совместимо с backfill-правилом из п.4). Валидатор `line_kind`/`direction` в `dds_article_budget.py:123` и `:396` расширяется явной проверкой согласованности с `contract_roles.cash_flow_direction(contract.kind)` по правилу п.3. Логика уникальности статьи (`:388–:409`) получает `direction` в составе ключа. Существующие суммы, статусы и связи не переписываются backfill'ом.

## Согласование с ТЗ

ТЗ v6.0 §27.1 описывает каноническую финансовую цепочку для расходной стороны; доходная сторона в редакции §27.1 не описана. Этот ADR — расширение модели бюджета, принятое отдельным решением владельца, а не трактовка существующего §27.1.

## Что этот ADR не решает

- Не меняет поведение `CashFlowEntry` — там направление уже было.
- Не вводит распределение бюджета по этапам ГПР — отдельный ADR, см. `ADR-GPR-PER-CONTRACT-BUDGET-ALLOCATION-RU.md`.
- Не объявляет V6-05 выполненным — это решение модели, реализация и тесты идут отдельным PR.

## Обязательные тесты реализации

- Создание доходной строки (`direction=inflow`) на `customer`/`revenue_subcontract` — проходит; на `downstream_subcontract`/`supply` — 422.
- Создание расходной строки (`direction=outflow`) на `downstream_subcontract`/`supply` — проходит; на `customer`/`revenue_subcontract` — 422.
- `legacy_unclassified` строка с `direction=NULL` не участвует в расчёте маржи; маржа считается только по подтверждённым строкам с явным `direction`.
- Смена `contract_kind` после создания бюджетной строки не переписывает `direction` существующей строки автоматически (явный пересчёт не входит в это решение).
- Уникальность аналитической статьи учитывает `direction` в ключе: доходная и расходная строка с одинаковым нормализованным названием на одном договоре — две разные строки, не конфликт.
