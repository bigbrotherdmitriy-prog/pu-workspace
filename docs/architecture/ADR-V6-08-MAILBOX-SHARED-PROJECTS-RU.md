# ADR-черновик: один рабочий ящик на много проектов одного владельца (V6-08)

Статус: **черновик, ждёт решения владельца.** Код не менялся, прод не трогался. Подготовлено в ночь закрытия MVP-5 (07/08.10.2026), пока владелец недоступен для проверки — решение о пункте 2 ниже требует его явного согласия, т.к. оно реально ослабляет существующую границу безопасности (пусть и искусственную для данного случая).

## Контекст и бизнес-факт (откуда это вообще взялось)

Владелец лично ведёт ~24 проекта с одного рабочего Gmail-ящика; весь смысл AI-секретаря — автоматически разбирать, какое письмо к какому проекту относится. Это не редкий случай — это основной сценарий использования продукта.

При закрытии MVP-5 обнаружено: текущая реализация mailbox rollout (`backend/app/mailbox_identity/`) в трёх независимых местах жёстко предполагает **один проект = единственный текущий владелец ящика в любой момент времени**. Из-за этого при каждой переротации OAuth-токена (переподключении Gmail из контекста ЛЮБОГО проекта) все остальные проекты, которые уже были подключены к этому же ящику, автоматически и незаметно теряют доступ — без ошибки, без уведомления, просто через несколько шагов начинают получать `mailbox_cutover_not_ready` / `_deny()`.

**Проверено по базе (read-only, 07.10.2026):** реально заблокирован сейчас только **проект №17** — единственный, у кого вообще есть `enabled=true` cohort-строка (на generation=6, при текущем generation=11). Остальные проекты (12, 14, 15, 16, 24), владевшие ящиком в разное время, никогда не включали pilot-rollout и просто используют обычный (не-AUTO) путь обработки почты — они не «осиротели», они и не были подключены к пилоту. Риск в том, что **любой** следующий проект, который включит rollout, окажется в том же капкане при следующей чужой переротации — сейчас пострадавший один, но конструкция системная, не разовая.

## Три места, где зашито предположение «один проект»

### 1. `google_oauth_tokens.project_id` → `change_project_cohort`, `renew_project_mailbox_authority`

Оба метода (`backend/app/mailbox_identity/service.py:338`, `authority.py`) жёстко требуют:
```python
token.project_id != project_id  # -> _fail()
```
Токен конкретного поколения принадлежит ровно одному проекту (тому, из чьего контекста шло OAuth-подключение). Любой другой проект того же владельца не может даже заявить права на это поколение.

**Предлагаемая правка (низкий риск):** заменить проверку на «проект токена и целевой проект — в одной организации, и actor — owner целевого проекта» (роль уже проверяется отдельно, остаётся):
```python
token_project = db.get(Project, token.project_id)
if token_project is None or token_project.organization_id != organization_id:
    _fail()
# (убрать: token.project_id != project_id)
```
Это не ослабляет защиту от чужих организаций — только снимает искусственное требование «тот же самый проект», которое и так уже дублируется проверкой owner-прав на целевой проект.

### 2. `MailboxAuthorityState.scope_project_id` — сужение до одного проекта при продлении

`renew_project_mailbox_authority` **всегда** пишет `scope_project_id = command.project_id` (узкий scope на один проект), и `require_mailbox_authority` затем жёстко требует `project_id == row.scope_project_id`. Таблица имеет уникальный ключ `(organization_id, mail_connection_id, principal_kind, principal_id)` — **одна строка на пользователя**, не на пару (пользователь, проект). Значит, после продления для проекта А мандат физически не может одновременно обслуживать проект Б — ровно та же проблема, что и с пунктом 1, но на уровень выше.

Комментарий в коде («renewed grants are always narrowed») — это осознанное решение автора, не случайность. Вероятно, задумывалось как доп. защита «не позволять случайно расшириться на лишний проект». Для одного владельца, ведущего 24 своих проекта с одного ящика, это превращается в постоянную помеху, а не защиту.

**Два варианта, нужно явное решение владельца:**

- **Вариант 1 (рекомендую): не сужать scope для owner-принципала.** Если actor одновременно owner и токена-источника, и целевого проекта (т.е. это буквально один и тот же человек, что и есть у вас) — оставлять `scope_project_id = NULL`, `scope_credential_generation = <новое поколение>` (сужение по поколению сохраняется — это и есть защита от использования отозванного/старого токена, самое важное свойство). Тогда `require_mailbox_authority` для `scope_project_id IS NULL` просто не проверяет равенство project_id — доступ открыт для любого проекта той же организации, где actor — owner, на текущем поколении.
- **Вариант 2 (строже, медленнее в реализации): множественные мандаты.** Убрать уникальность по `principal_id` и добавить `project_id` в ключ — одна строка на (пользователь, проект). Безопаснее по изоляции, но: миграция данных, больше кода, велик шанс сломать что-то ещё при таком объёме правок ночью без возможности проверить с вами.

### 3. Авто-создание `MailboxProjectCohort` — только для проекта-владельца токена

В `bind_verified_google_subject` (service.py) cohort-запись при ротации создаётся **только** для `project = token.project_id`-шного проекта, `enabled=False`. Для остальных проектов такой строки никогда не появляется — значит, `change_project_cohort` (который требует существующую строку) не может их «переключить», даже если пункты 1 и 2 выше починить.

**Предлагаемое дополнение (чисто additive, ничего не трогает):** новый метод `join_project_cohort(db, *, organization_id, project_id, mail_connection_id, credential_generation, binding_epoch, actor, authority_version)`:
- Проверки те же, что в `change_project_cohort` (owner-членство, не архивирован, mail/identity/generation активны, токен — через правку п.1, `require_mailbox_authority(permission="rollout", ...)` через правку п.2).
- Если cohort-строки нет — создать (`enabled=True` сразу, раз explicit join = explicit confirm) с `record_version=1, changed_by_user_id=actor.id`.
- Если есть, но `enabled=False` — включить (как сейчас делает `change_project_cohort`).
- Audit-событие `mailbox_project_cohort_joined` (отдельное от `mailbox_project_cohort_changed`, чтобы в журнале было видно «новое подключение», а не просто флип флага).
- HTTP: `POST /integrations/mailbox-rollout/join` (рядом с существующим `PATCH /integrations/mailbox-rollout`), тело — то же самое + `project_id`.

## Что НЕ трогаем

- Лестницу cutover-флагов (`rollout_flags_are_valid`) и запрет `primary_read`/`actions` после сужения scope — это ортогонально, остаётся как есть.
- Append-only таблицы (`v54_mailbox_credential_generations`, `*_origin_bindings`, `*_origin_decisions`) — не трогаем вообще, откат там и так только через новую запись.
- Сам процесс ротации (`bind_verified_google_subject`) — никакого авто-переноса других проектов, как было решено ранее ночью (это бы противоречило явному docstring модели про изоляцию). Вместо автопереноса — explicit join по требованию, через новый метод из п.3.

## План реализации (когда будет решение по варианту п.2)

1. Правка п.1 (token.project_id → org-scope) — backend/app/mailbox_identity/service.py + authority.py, + тесты на обе функции (разрешить cross-project-same-org, запретить cross-org).
2. Правка п.2 (выбранный вариант) — backend/app/mailbox_identity/runtime.py (`require_mailbox_authority`) + authority.py (`renew_project_mailbox_authority`), + тесты: мандат, продлённый для проекта А владельцем, работает и для проекта Б того же владельца/организации на текущем поколении; не работает для чужой организации.
3. Новый метод `join_project_cohort` + эндпоинт (п.3) + тесты: join создаёт и включает cohort; повторный join идемпотентен; join другим (не-owner) пользователем отклоняется; join для чужой организации отклоняется.
4. Полная регрессия (`pytest`, фронтенд `pnpm test`), как во всех PR сегодняшней ночи.
5. Деплой — **отдельным, осознанным шагом с владельцем на связи** (как и всё в этой системе до сих пор), не автоматически вслед за мержем — это первое реальное изменение, которое затрагивает механизм авторизации живой почты, а не только внутреннюю бухгалтерию пилота.
6. После деплоя: владелец лично вызывает join для проекта №17 на текущем поколении (11) — это разовое ручное действие, не автоматика. Остальные проекты join не требуют, пока сами не захотят включить rollout.
