# ADR: два параллельных механизма синхронизации одного Gmail-ящика (V6-09)

Статус: **реализовано и закрыто на проде 09.10.2026.** Владелец выбрал полноценный перевод планового сбора на общий механизм (PR #141, деплой SHA `6c40213ddd6e8414db48bb940a2694a9a55a0769`). Проверено на реальном инциденте: проекты 14/16/24 падали с `RefreshError: invalid_grant` при каждой чужой переротации до деплоя, после деплоя синхронизируются чисто (подтверждено прямой проверкой production-БД). Текст находки ниже сохранён как есть для истории.

## Контекст обнаружения

При восстановлении проекта №17 (после ADR-V6-08) владелец лично переподключил Google-аккаунт через обычный экран интеграций проекта. Это вызвало новую ротацию общего `credential_generation` (11 → 12) в системе `mailbox_identity` — ожидаемо, починено тем же механизмом (`join_project_cohort` повторно на поколении 12).

Побочный эффект, обнаруженный сразу после: плановая `gmail.sync` (включена в эту же ночь, см. ниже) немедленно показала падения на трёх **других** проектах:

```
ERROR:app.automations.gmail:Automatic Gmail synchronization failed for project 14
ERROR:app.automations.gmail:Automatic Gmail synchronization failed for project 16
ERROR:app.automations.gmail:Automatic Gmail synchronization failed for project 24
google.auth.exceptions.RefreshError: ('invalid_grant: Token has been expired or revoked.', ...)
```

Подтверждено по журналу аудита (`gmail_auto_sync_failed`, `error=RefreshError`) для всех трёх проектов, в двух последовательных прогонах (09:34 и 09:35, 09.10.2026).

## Факт архитектуры

В кодовой базе существуют **два независимых** механизма чтения/синхронизации почты для одного и того же Google-аккаунта:

1. **Новый, общий (`backend/app/mailbox_identity/`)** — модель `ConnectionIdentity`/`MailConnection` + append-only `MailboxCredentialGeneration`. Один аккаунт = одна текущая "живая" идентичность с явным, версионируемым поколением. Правильно спроектирован для сценария "один Gmail-ящик на много проектов" — это и чинил ADR-V6-08.

2. **Старый, прямой (`backend/app/automations/gmail.py` + `backend/app/api/gmail.py`)** — каждый проект хранит **свою собственную** строку `GoogleOAuthToken` (`project_id` — первичный владелец), независимо от других проектов, даже если все они фактически используют один и тот же Google-аккаунт. `sync_authorized_projects_once()` каждые `GMAIL_AUTO_SYNC_INTERVAL_SECONDS` (по умолчанию 300с) проходит по **всем** таким токенам и для каждого вызывает `sync_gmail_project()`.

Google аннулирует (`invalid_grant`) старые refresh-токены того же аккаунта+OAuth-клиента+набора scope при новом согласии (новом "Подключить Google"). Значит: **любое** переподключение любого проекта на старом механизме отзывает refresh-токены всех остальных проектов на этом же механизме для того же аккаунта — ровно та же "one owner, one mailbox" ловушка, что и в ADR-V6-08, но в другом, не связанном с ним коде.

## Проверено по факту (09.10.2026, read-only)

- Всего строк `GoogleOAuthToken` в системе: **12** (12 проектов когда-то подключали Gmail напрямую через старый механизм).
- Из них упали в первом же цикле после сегодняшнего переподключения: **3** (проекты 14, 16, 24) — `RefreshError: invalid_grant`.
- Остальные не проверялись индивидуально (могли быть не затронуты в этот раз, или уже были сломаны ранее по той же причине — не выяснялось).

## Почему это не починено ADR-V6-08

ADR-V6-08 чинил ровно три места в `mailbox_identity` (новом механизме). Он не знал и не трогал старый, параллельный `automations/gmail.py`-путь — это была отдельная, ранее не обнаруженная часть той же системной проблемы.

## Что НЕ делаем сейчас

Хотфикс (например, выборочно починить токены 14/16/24 переподключением) решает симптом на сегодня, но не корень: следующее переподключение любого проекта на старом механизме снова отзовёт токены остальных. Чинить точечно каждый раз — не масштабируется.

## Предполагаемое направление решения (не реализовано, нужно решение владельца)

Перевести старый механизм (`automations/gmail.py`) на тот же `mailbox_identity`/`ConnectionIdentity` источник правды, которым уже пользуется новый — т.е. `sync_authorized_projects_once()` должен резолвить токен через текущее поколение общей идентичности (как это уже делает `resolve_project_gmail_read` в новом коде), а не через собственную отдельную строку `GoogleOAuthToken` на проект. Это не малая правка — затрагивает едва ли не весь `automations/gmail.py` и, вероятно, миграцию данных (12 существующих `GoogleOAuthToken` строк). Требует отдельного ADR с вариантами, по аналогии с ADR-V6-08, и отдельного решения владельца перед реализацией.

## Открытый вопрос владельцу

Переходить ли на объединение старого и нового механизмов (большая работа, полноценное решение) — или точечно чинить переподключением по мере поломки отдельных проектов (минимальная работа, та же ловушка повторяется каждый раз)?
