# Policy matrix и минимальный пилот

PROPOSED. Это проект правил, не активная конфигурация и не решение владельца.
Решение MVP5/MVP6 находится в [README](README.md). Значения лимитов ниже —
предлагаемые acceptance fixtures, а не действующие продуктовые настройки.

## Матрица

| Тип / стадия | Default | AUTO в MVP5 | Risk / reversal | Обязательный gate |
|---|---|---|---|---|
| Чтение внутренних данных / READ | ASSIST | Не требуется разрешение EXECUTE | По чувствительности; без бизнес-эффекта | RBAC, tenant ACL, privacy; READ не даёт права писать |
| Анализ документа / ANALYZE | ASSIST | Не даёт права применять вывод | По данным; без бизнес-эффекта | Source/evidence access; внешняя обработка только по AI data policy |
| Черновик письма, задачи, финансового предложения / DRAFT | ASSIST | Нет исполнения | Без назначения обязательств | Сохранение как черновик, без send, assigned Task, CashFlow fact |
| Замороженное предложение / PROPOSE | ASSIST | Не исполнение | Risk будущего эффекта | Hash/version, evidence refs, доступ к проекту |
| `task.internal.create` / EXECUTE | CONFIRM | Только явная LOW allowlist policy в scope/сроке | LOW только при всех ограничениях; COMPENSATABLE | Create task permission, применимое approval либо server AUTO grant, preflight |
| `task.internal.cancel` / EXECUTE | CONFIRM | Запрещён в пилоте | LOW/MEDIUM по состоянию; COMPENSATABLE | Собственные права/approval; expected task version; отсутствие внешних эффектов |
| `message.external.send` / EXECUTE | CONFIRM | Запрещён | Не ниже HIGH; IRREVERSIBLE | Send permission, человек подтверждает конечное содержимое и адресатов |
| `message.external.corrective_send` / EXECUTE | CONFIRM | Запрещён | HIGH; IRREVERSIBLE | Новый action, новый approval, ссылка на исходное письмо |
| Изменение/перемещение оригинальных файлов | Existing CONFIRM/owner guards | Не расширяется | По adapter capabilities, не считать всегда REVERSIBLE | Существующие safe-copy/source guards сохраняются; v5.4 gate вводится отдельным этапом |
| Подтверждение реквизитов | CONFIRM | Запрещён | HIGH; версионированные сведения | Отдельное решение человека по конкретным реквизитам |
| Создание/утверждение финансового обязательства | CONFIRM | Запрещён | HIGH | Финансовые полномочия; утверждённые договор, этап, сумма, валюта, сроки |
| Подтверждение факта оплаты | CONFIRM | Запрещён | HIGH | Пользователь подтверждает факт, сумму и дату; это не команда банку |
| Неизвестный тип / UNKNOWN risk | DENY | Запрещён | UNKNOWN | Регистрация server action catalog и отдельное решение |

Effective permission — пересечение RBAC, project/organization scope, policy,
privacy, target constraints и approver authority. Любой DENY побеждает allow.
CONFIRM не обходит запрет privacy/provider. ASSIST не обходит READ ACL.
И policy editor, и approver должны иметь текущие необходимые полномочия;
текущее admin-role bypass не является универсальным разрешением AUTO.

## Пилот create internal task

CONFIRM-путь: AI/человек создаёт proposal → сервер фиксирует точные поля и
источники → показывает человеку target/effects/risk → человек утверждает
revision/hash → непосредственно перед выполнением gate повторяется → одна
транзакция создаёт Task, TaskHistory и receipt/ledger.

Ограничения LOW/AUTO для данного пилота:

- Только одна внутренняя Task в явно разрешённом проекте, без внешней публикации,
  писем, календарей, provider actions и создания финансового обязательства.
- Название, описание, assignee_user_id, due_date и source/context refs уже заморожены.
  Assignee — действующий участник проекта; свободный текст не исполняется.
- Contract/finance mutation и cascade effects не входят в разрешённый effect set.
  Если helper создаёт Obligation либо публикует задачу, этот helper не подходит
  без отделения побочного эффекта. `needs_review=true` не заменяет approval.
- У policy есть scope, версия, enabled_by, enabled_at, expires_at, policy hash
  и явно заданные лимиты. Пример fixture: не более 5 задач в час на проект,
  одна задача на один semantic action key. Квота резервируется атомарно с action,
  иначе два workers могут превысить её. Ретраи одного effect не расходуют квоту повторно.
- Evidence owner подтверждает доступ, целостность и свежесть всех refs. В пилоте
  анализ на низкой уверенности/unverified evidence не допускается в AUTO:
  CONFIRM при разрешении policy либо BLOCKED, если данные недоступны/изменились.
- Policy явно разрешает действие от конкретного authenticated principal/service
  mandate. Scheduler/модель не выбирает удобного участника как «человека-approver».
  Для AUTO ledger указывает server policy decision и человека, включившего policy;
  человеческий approval на конкретное действие не фабрикуется.

При отсутствии approval в CONFIRM — AWAITING_APPROVAL. При отсутствии явного
AUTO grant — не выполнять; можно предложить CONFIRM, но нельзя молча менять режим
уже замороженной revision. При изменении policy нужен новый freeze/decision.

## Cancel и обратимость

Отмена созданной задачи — **новый** `task.internal.cancel` с target Task ID/version
и `compensates_action_id` исходного create. Это COMPENSATABLE: задача, история
назначения и прошедшее время не исчезают. Оно удовлетворяет сценарию ТЗ
«отменить созданную задачу с отдельным аудитом», не обещая буквальное стирание эффекта.

В пилоте можно отменить только внутреннюю ещё assigned задачу без публикации,
выполнения, финансовых связей, зависимых действий и незавершённого внешнего outcome.
Если задача уже изменилась, действие блокируется и требует нового предложения.
Повтор команды с тем же action key возвращает receipt; отмена уже отменённой
задачи другим action не выдаётся за новый произведённый эффект.

`REVERSIBLE` допускается в каталоге, например для изменения внутреннего атрибута,
если прежнее значение можно восстановить conditional-write и побочных эффектов
не было. Этот тип не добавляется в пилот. Восстановление атрибута всё равно новое
действие с собственным approval. Для частично применённого Organizer batch
compensation ведётся по фактическим receipts элементов, не по статусу job.

`update_task` сейчас способен после commit вызвать внешнюю публикацию ранее
исполненной задачи. Поэтому facade пилота не должен просто вызывать существующий
HTTP endpoint cancel: нужен узкий DB-only helper того же модуля и проверка effect set.

## Письма и финансы

Письмо: подтвердить точные To/Cc/Bcc, sender account, subject/body, вложения и
reply/thread context. Provider response не подтверждает прочтение или выполнение
задачи. `sent` не переводит связанную задачу в completed; подтверждение выполнения
остаётся отдельным доменным решением. Corrective email только добавляет новое письмо.

Финансовые решения независимы:

1. ANALYZE счёта создаёт извлечённые данные/evidence и DRAFT; не платёж и не
   утверждённое обязательство. Низкая уверенность требует ручной проверки.
2. Approval реквизитов связывается с отдельной версией реквизитов; изменение
   номера счёта/получателя аннулирует его применимость. Это не факт оплаты.
3. Approval обязательства фиксирует договор/этап ГПР/статью ДДС, сумму, валюту,
   условия и дату. Автоматическое создание обязательства без нужного grant запрещено.
4. Факт оплаты подтверждает пользователь с финансовыми правами: точные
   actual_amount, currency, paid_at и связь с обязательством показываются до
   подтверждения, без скрытой подстановки текущей даты/плановой суммы после approval.
   Основание может быть human attestation; банковская выписка не обязательна.
5. Запись факта и соответствующая корректировка ДДС — один заявленный effect set
   с идемпотентным receipt; повтор confirmation не удваивает затраты. Исправление
   факта — новое audited action, не удаление истории.

Текущий `confirm_payment` не исполняет платёж в банке; контракт не добавляет банк,
банковский credential или обязательную выписку. Изменения финансовых handlers
не входят ни в этот документационный commit, ни в task-only пилот.
