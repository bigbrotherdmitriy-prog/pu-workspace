# ADR: ГПР по договору — распределение бюджета по этапам

Статус: ADR утверждён владельцем 06.10.2026 по итогам пошагового разбора вариантов. Реализация разрешена с учётом ограничений ниже. Владелец отдельно отметил: при необходимости решения этого документа можно пересмотреть после начала реализации.

Все числовые примеры и названия в этом документе вымышлены. Производственные идентификаторы, суммы и координаты документов остаются вне Git.

## Что уже есть

`ScheduleBaseline.contract_id` уже существует (`execution_finance.py:11–24`) — ГПР уже привязан к одному договору. `ScheduleItem` привязан к `baseline_id`, а не к договору напрямую. «ГПР по договору» в смысле «один baseline — один договор — много этапов» уже реализовано.

## Чего не хватает

Бюджетная строка договора — одна на весь договор (см. ADR-DDS: «Договор даёт одну строку на общую сумму»). Этапов ГПР внутри договора может быть много. Нет способа показать, сколько из бюджета строки относится к какому этапу: нельзя сравнить прогресс ГПР с освоенным бюджетом по этапу. MVP-4 сознательно отложил это решение (`docs/audits/mvp4-schedule-budget-links-future-adr.md`); текущая тройка contract+schedule_item+budget_line в ДДС даёт только прослеживаемость операции, не распределение суммы.

## Решение владельца

1. **Вводится таблица `schedule_budget_links`** — many-to-many между `budget_line_id` и `schedule_item_id`. Отклонённые варианты: оставить одну строку на договор без распределения (недостаточно для этапной себестоимости); считать распределение только на лету из фактов ДДС без хранения плана по этапу (не отвечает на вопрос «сколько запланировано на этап»).
2. **Распределение задаётся только суммой** (`amount`), без параллельного процента. Процент, если нужен в UI, вычисляется и показывается как производная от суммы — не хранится отдельно, чтобы не держать два параллельных представления в синхронизации.
3. **Сумма распределений по этапам не может превышать `planned_amount` бюджетной строки — жёсткий запрет**, а не предупреждение. Попытка создать/изменить распределение, которое в сумме с уже существующими превысит `planned_amount` строки, отклоняется (422) без частичной записи.
4. **При создании новой ревизии (версии) baseline существующие распределения сбрасываются.** Новая версия ГПР не переносит автоматически старые распределения на новые `schedule_item_id` (которые физически другие записи с другими id). Для новой версии требуется новый preview и отдельное подтверждение владельца — без этого распределений нет.
5. **Распределение не влияет на `committed_amount`/`actual_amount` бюджетной строки.** Эти суммы остаются на уровне строки целиком, не разбиваются по этапам в рамках этого решения. Распределение касается только `planned_amount` (план); этапная проекция факта/обязательства — отдельная задача, не входящая в это решение.

## Правила, зафиксированные решением (ранее открытые вопросы)

- Удаление этапа, на который было распределение: распределение этапа удаляется вместе с ним (явный каскад), бюджетная строка не затрагивается — высвобождается соответствующая сумма из «занятого» объёма `planned_amount`.
- Валидация принадлежности: `budget_line_id` и `schedule_item_id` в одной записи `schedule_budget_links` должны принадлежать одному проекту и одному договору — иначе 422.

## Миграция

Новая таблица `schedule_budget_links(id, budget_line_id, schedule_item_id, amount, note, created_by_user_id, created_at)` с FK на `budget_lines` и `schedule_items` (ondelete="CASCADE" для обеих связей, в соответствии с правилом удаления этапа выше). Backfill не требуется — таблица создаётся пустой; существующие тройки contract+schedule_item+budget_line в ДДС не затрагиваются и продолжают работать как прослеживаемость, независимо от наличия или отсутствия записи в новой таблице.

## Согласование с ТЗ

ТЗ v6.0 §27.1 требует тройку contract+schedule_item+budget_line для операций, но не требует распределения бюджета по этапам. Этот ADR — расширение модели, а не трактовка §27.1; он не ослабляет и не заменяет существующий валидатор тройки.

## Что этот ADR не решает

- Не меняет каноническую тройку contract+schedule_item+budget_line для ДДС-операций.
- Не вводит направление/доходный бюджет — это отдельный ADR, см. `ADR-V6-05-INCOME-BUDGET-RU.md`.
- Не распределяет `committed_amount`/`actual_amount` по этапам (см. п.5 решения) — если это понадобится, требуется отдельное решение владельца.

## Обязательные тесты реализации

- Сумма распределений в пределах `planned_amount` строки — создаётся; превышение — 422, без частичной записи.
- Распределение на `schedule_item`/`budget_line` разных проектов или разных договоров — 422.
- Новая ревизия baseline: старые распределения не появляются автоматически у новых `schedule_item` этой ревизии; нужен новый явный preview/подтверждение для их создания заново.
- Удаление `schedule_item` с распределением — распределение удаляется каскадно, `planned_amount` строки не меняется.
- Изменение `committed_amount`/`actual_amount` бюджетной строки не требует и не трогает записи `schedule_budget_links`.
