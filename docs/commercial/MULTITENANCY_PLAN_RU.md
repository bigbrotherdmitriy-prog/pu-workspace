# Технический план мультиарендности PU Workspace

**Роль:** архитектор. **Целевая модель:** Organization = арендатор. **Факты:** 14/39 моделей с `organization_id`, роли проекта viewer/member/editor/manager/owner, фактически один владелец.

---

## 0. Целевая модель (коротко, для контекста задач)

- **Арендатор** — `Organization`. Все бизнес-данные (проекты, документы, письма, задачи, интеграции) принадлежат ровно одной организации.
- **Пользователь** глобальный, но его доступ определяется **членствами** в организациях: `OrganizationMember(user_id, organization_id, role)`.
- **Роль в организации:** `owner` / `admin` / `member` (минимум). Роли проекта (`viewer/member/editor/manager/owner`) остаются как есть, но их выдача возможна только для участников организации.
- **Проект** принадлежит организации → `Project.organization_id NOT NULL`.
- **Изоляция** — на уровне запросов: любой доступ к ресурсу проходит через проверку `resource.organization_id == current_organization_id` **(или, если арендатор ещё не введён в запросе, через скоуп по членствам пользователя)**. Отдельный слой «tenant filter» + тесты на утечку.
- **Интеграционные учётки (Google, Яндекс, Telegram, почта, коннектор)** — на организацию, не на пользователя.
- **Лимиты тарифа** — на организацию: пользователи, проекты, документы/мес, доступные адаптеры.

**Инвариант**: невозможно получить данные чужой организации ни одним API-вызовом, ни через вложенные сущности (session → proposal → action → document → history → drive_connection). Это то, что проверяют тесты на утечку.

---

## 1. Принципы разбиения на задачи

- **1 PR = 1 задача = ≤300 строк**, включая тесты. Если миграция + код модели не влезают — разделяем.
- **Порядок:** сначала фундамент (БД, членства, контекст запроса), затем волна за волной закрываем модели (сначала те 25, где `organization_id` ещё нет), затем регистрация/приглашения, лимиты, учётки интеграций, и только потом публичные сценарии.
- **Тесты на утечку** — обязательны на каждой волне, не отдельной «финальной» задачей. Помечены флагом 🚨.
- **Пометка риска утечки** 🚨 — задача меняет фильтрацию/скоупинг/права на данные.

Легенда: 🚨 — задача, где особенно высок риск утечки между арендаторами.

## 2. Задачи (в порядке выполнения)

### Блок A. Фундамент: организации и членства

**A1. Сущность Organization и роль организации**
- **Цель:** каноничная модель `Organization` + роль `owner/admin/member` в ней.
- **Файлы:** `backend/app/models/organization.py` (новый), `backend/app/models/__init__.py`, миграция Alembic.
- **Готово:** таблица `organizations`, `organization_id` у членств валиден; `OrganizationMember` создан как отдельная таблица (если ещё нет).
- **Тесты:** unit на создание/уникальность `slug`, membership FK.

**A2. OrganizationMember: роль и инварианты**
- **Цель:** одна активная запись (user, org), роль из enum, даты приглашения/активации.
- **Файлы:** `backend/app/models/organization.py`, `backend/app/schemas/organization.py` (новый), миграция.
- **Готово:** UNIQUE(user_id, organization_id), тест на запрет двух ролей у одной пары.
- **Тесты:** unit.

**A3. Контекст арендатора в API**
- **Цель:** резолвер `current_organization` из запроса (заголовок `X-Organization-Id` + fallback на «организацию по умолчанию пользователя»), Dependency FastAPI.
- **Файлы:** `backend/app/deps.py` (или аналог), `backend/app/api/*` (только подключение).
- **Готово:** в логах видно `org_id`; неавторизованный получает 401/403.
- **Тесты:** 🚨 unit — пользователь без членства в запрошенной organization получает 403.

**A4. Скоупинг выборки проектов по организации** 🚨
- **Цель:** `GET /projects` возвращает только проекты организаций пользователя (или только текущей).
- **Файлы:** `backend/app/api/projects.py`, `backend/app/services/project_service.py` (если есть).
- **Готово:** кросс-организационный доступ невозможен; параметры фильтра проверены.
- **Тесты:** 🚨 интеграционный — 2 org, 2 user, 2 проекта: каждый видит только свой.

**A5. Скоупинг вложенных ресурсов проектов** 🚨
- **Цель:** session / proposal / action / document / history / drive_connection доступны только если `project.organization_id == ctx.org_id`.
- **Файлы:** сервисные функции этих сущностей, helpers.
- **Готово:** один общий хелпер `ensure_project_visible(project_id, ctx)`, применяется во всех роутах.
- **Тесты:** 🚨 интеграционные — по одному на каждую сущность из списка.

**A6. Журнал попыток кросс-доступа (audit)**
- **Цель:** писать в `audit_log` факт отказа по организации (для разбора инцидентов).
- **Файлы:** `backend/app/models/audit_log.py`, `backend/app/services/audit.py`.
- **Готово:** событие `tenant_access_denied` с `user_id`, `org_id`, `resource`.
- **Тесты:** unit на запись; интеграционный — отказ порождает запись.

### Блок C. Миграция существующих данных в «организацию владельца»

- **Тесты:** unit на идемпотентность.

**C2. Backfill `organization_id` для всех арендуемых таблиц**

**C3. Включение NOT NULL после успешного backfill**

**C4. Проверка целостности: члены проектов в одной организации** 🚨

- **Файлы:** `projects.py`, `org.py`, `documents.py`.
- **Готово:** лимиты организации не пересекают чужие (проверка по своей org).

**E5. Мягкий/жёсткий лимит + апселл-текст**
- **Цель:** 80% → предупреждение в UI/Telegram, 100% → блок нового действия (не чтения).
