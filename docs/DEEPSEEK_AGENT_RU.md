# Изолированный DeepSeek coding agent

Workflow `DeepSeek isolated coding agent` запускается владельцем репозитория вручную из `main` с номером открытого issue. Это один запуск на задачу, без копирования кода и команд. В issue укажите ожидаемое поведение, критерии приемки и существующие пути исходников в обратных кавычках: именно эти файлы попадут в контекст (до 12 файлов). Обсуждение issue и внешние ссылки агент не читает.

## Однократная настройка

1. В Settings → Secrets and variables → Actions создайте secret `DEEPSEEK_API_KEY`. Не вставляйте ключ в issue, чат, код или логи. Агент не читает production secrets.
2. Создайте repository variable `DEEPSEEK_MODEL` с доступным в вашем DeepSeek API идентификатором модели. На момент подготовки официальная документация перечисляет `deepseek-flash` и `deepseek-v4-pro`; сверяйте доступность в вашем аккаунте. Нет автоматического fallback, GPT-6 или другого провайдера.
3. В Settings → Actions → General включите **Allow GitHub Actions to create and approve pull requests**. Агент использует только создание draft PR, не approval. Без этого права публикация завершится ошибкой после тестов.
4. Слейте установочный PR после проверки. Запускайте workflow только из `main`.

## Границы доступа

- Только `ubuntu-latest`, никаких self-hosted runners, SSH, production URL, Docker socket внутри тестовых контейнеров или deployment environments.
- Workflow имеет `permissions: {}`; запросу выдаются только чтение contents/issues и DeepSeek key. Тестовому заданию — contents:read, без API-ключа. Публикатору — contents:write/pull-requests:write, без DeepSeek key; он не исполняет предложенный код.
- Ответ модели — строгий JSON с полным содержимым до 8 файлов / 100 КБ. Никаких команд, патчей shell, tools, путей за пределами allowlist, скрытых файлов, symlinks, зависимостей, workflows, миграций или инфраструктуры. Изменение исходников требует тестового файла. Это проверяет наличие теста, а не его качество: нужен review.
- Issue и исходники считаются недоверенными. System prompt — дополнительная мера; реальная граница обеспечивается валидатором путей, отсутствием инструментов модели, разделением заданий и контейнерами без сети/секретов. Контекст отправляется только на фиксированный HTTPS endpoint DeepSeek; redirects запрещены.
- Зависимости тестов устанавливаются из доверенного base до применения предложения. Предложенный код выполняется только непривилегированным пользователем в контейнере с read-only filesystem, временными каталогами, лимитами CPU/RAM/PID и `--network none`. Логи модели и произвольный вывод тестов не публикуются. При ошибке — остановка без PR; это усложняет диагностику, но исключает workflow-команды из вывода тестов.
- Публикатор повторно валидирует тот же immutable artifact текущего запуска, проверяет неизменность `main`, создаёт уникальную `ai/deepseek-<run>-<attempt>` ветку и draft PR через GitHub API. Он не делает force push, merge, approve или deploy. Артефакт хранится один день, содержит только предлагаемую правку и SHA base.

## Проверки и ограничения первого этапа

Запускаются unit-тесты самого валидатора, затем полный `backend/tests` и frontend `pnpm check` / `pnpm test` без сети. PostgreSQL, Java и внешние сервисы в этом контуре не предоставляются: если тестам они необходимы, задача остановится, а не обойдет проверку. Это консервативный первый этап, не замена существующей PostgreSQL CI, сборки и e2e. Образам нужны доступные реестры и работающий Docker на GitHub-hosted runner. Версии базовых Docker-образов заданы тегами; actions закреплены SHA.

PR, созданный стандартным `GITHUB_TOKEN`, обычно не запускает другие workflows автоматически. Не используйте PAT с широкими правами для обхода этого ограничения. Перед merge нужно явно запустить полную CI на ветке или добавить отдельный безопасный механизм проверки. Текущий `ci.yml` не имеет `workflow_dispatch`; соответствующее расширение CI — отдельная задача. Draft PR не означает готовность к production.

Production diagnostic workflow остается без изменений и не запускается агентом. Настройки runner groups и branch protection этим PR не меняются. Администратор с правом редактировать workflow по-прежнему может изменить его границы; JSON-агент не является защитой от администратора репозитория. Даже изоляция контейнера не гарантирует отсутствие всех уязвимостей; код требует review.
