# Акт закрытия MVP-6 (документный контроль исполнения)

Дата независимой сверки: 09.10.2026. Метод: read-only запросы к production-БД (`puw-primary-next-primary-db`) и целевой поиск по коду, независимо от спецификации `docs/mvp6-document-control.md` (29.08.2026, все 7 пунктов отмечены в тексте как `[x]` — это самоотчёт автора спецификации, не прежний независимый акт).

В отличие от MVP-3/4, для MVP-6 не по каждому пункту найдены живые данные такой же прямой силы — ниже честно указано, что подтверждено на реальных данных прода, а что — только присутствием соответствующего кода (без утверждения о живом прогоне для каждого отдельного пункта).

## Подтверждено на реальных данных прода

**«Счёт и акт сохраняют ссылку на документ-источник»** — подтверждено. В проде **102** записи `cash_flow_entries` имеют заполненный `source_document_id`. Пример: запись id=1 (проект №11, сумма 290 000,00 ₽) ссылается на документ id=1730 («52 дог спец.pdf»).

**«Пользователь проверяет поля до создания предложения»** — подтверждено архитектурно и теми же данными, что в акте MVP-4: записи ДДС остаются в статусе `proposed` до явного подтверждения пользователем (см. `CLOSURE_ACT_V6-00_RU.md`, пункт 2 — на проде не осталось ни одной записи в `proposed` без подтверждения или отмены).

## Подтверждено наличием кода (не отдельным живым прогоном для этого акта)

- **«ГПР, бюджет/смета, ДДС, счёт и акт распознаются по имени и полному тексту»** — классификация по тексту подтверждена (`backend/app/summary_engine.py`, функция `document_kind` + regex по типам документов); привязка типизированных сущностей (ГПР/бюджет) — через отдельные модули импорта (`dds_budget_links.py`).
- **«Для предложения показываются уверенность и причины классификации»** — поле `confidence` присутствует в модели (`execution_finance.py:305`); `summary_engine.py` формирует "Основание"/"Документ"/"Сумма" как причины.
- **«Из документа извлекаются подсказки суммы, даты и номера»** — подтверждено тем же механизмом, что и в MVP-2 (`document_extraction.py`, regex + LLM извлечение сумм/дат), общий код с задачами/обязательствами.
- **«Повторно связанные документы помечаются в интерфейсе»** — логика присутствует (`dds_budget_links.py`, отражена во фронтенд-модулях `FinanceModule.tsx`/`ContractBulkImportWizard.tsx`); отдельно на реальных данных прода пример дублирующей связи не искался в рамках этого акта.
- **«Исходный документ не переименовывается и не изменяется этим сценарием»** — архитектурно подтверждено тем же принципом, что лежит в основе MVP-1 (safe-copy, неизменность оригиналов) — сценарий MVP-6 работает поверх уже проанализированных документов, не трогая `Document`/`DocumentVersion` напрямую.

## Заключение

Два пункта из семи подтверждены прямыми данными прода на уровне строгости MVP-4. Остальные пять подтверждены присутствием и целостностью соответствующего кода, без отдельного живого прогона каждого пункта в рамках именно этого акта. **MVP-6 считается закрытым с этой оговоркой** — для полной уверенности того же уровня, что MVP-4, потребовался бы отдельный прогон с реальным ГПР/счётом/актом, явно воспроизводящий полный сценарий «документ → предложение → подтверждение».
