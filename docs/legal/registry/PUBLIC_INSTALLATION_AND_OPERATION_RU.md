# Публичная инструкция установки и эксплуатации

Документ не содержит production-секретов. Перед публикацией заменить поля `[ВЛАДЕЛЕЦ]`, `[URL]`, `[ВЕРСИЯ]` и проверить инструкцию на эталонном release SHA.

## Требования

- Linux x86_64, Docker Engine и Docker Compose;
- 4 vCPU и 8 ГБ RAM как стартовый пилотный профиль;
- PostgreSQL 16 в составе Compose либо совместимый отдельно управляемый экземпляр;
- постоянный диск, резервное хранилище, домен и TLS reverse proxy;
- исходящий доступ только к явно разрешённым подключаемым сервисам;
- современный браузер пользователя.

## Установка

1. Получить релиз `[ВЕРСИЯ/SHA]` от `[ВЛАДЕЛЕЦ]` и сверить опубликованный SHA-256.
2. Создать закрытый `.env` по `.env.example`. Сгенерировать собственные `APP_SECRET_KEY`, `TOKEN_ENCRYPTION_KEY`, `BOOTSTRAP_TOKEN` и пароль БД.
3. Не использовать credentials разработчика. При необходимости создать собственные OAuth/API credentials заказчика.
4. Запустить `docker compose build`, затем `docker compose up -d db`.
5. Применить миграции командой контейнера backend: `alembic -c alembic.ini upgrade head`.
6. Запустить API, workers и scheduler: `docker compose up -d`.
7. Проверить `/health`, `/api/readiness`, версию схемы, два worker heartbeat и тестовую задачу.
8. Создать первого администратора bootstrap-токеном и убрать bootstrap-доступ после использования.

## Эксплуатация

- ежедневно контролировать readiness, очередь, dead-letter, свободное место и backup;
- выдавать доступ по минимально необходимой роли;
- подтверждать внешние и финансовые действия вручную;
- обновлять только зафиксированным релизом после backup и теста восстановления;
- не помещать секреты, документы клиентов и production dump в Git.

## Резервное копирование и восстановление

Выполнять ежедневный шифрованный PostgreSQL dump и хранить его отдельно от сервера. Не реже раза в месяц проверять восстановление в изолированной БД. Перед восстановлением production остановить запись, создать аварийную копию и иметь подтверждённый путь отката.

Целевые RPO/RTO, срок хранения и ответственные: `[РЕШЕНИЕ ВЛАДЕЛЬЦА/ЗАКАЗЧИКА]`.

## Режим без внешнего AI

Не задавать ключ внешнего AI, отключить разрешение внешнего анализа в политике проекта и использовать локальное извлечение/OCR. Перед публичным заявлением об автономности провести тест, подтверждающий отсутствие исходящих запросов с содержимым документов. Текущий код содержит архитектурную возможность и policy-gate, но конкретный release должен пройти сетевой приёмочный тест.

Поддержка: `[ПУБЛИЧНЫЙ URL/EMAIL ВЛАДЕЛЬЦА]`.
