# MVP4 M4-02 — доказательства реквизитов договора

Дата проверки: 2026-09-05

База: `a19fffde54e51aee0b42220c83f6c19b1d3b9055`

Ветка: `codex/mvp4-contract-evidence`

## Граница результата

Реализован только безопасный срез M4-02: локальное детерминированное извлечение
реквизитов договора и привязка результата к неизменяемому Evidence. Весь MVP4
готовым не объявляется. Внешний AI, реальные документы, Google/Яндекс API,
production и оригиналы файлов не использовались.

## Аудит до изменения

- `_contract_financial_terms` возвращал сумму, аванс и удержание вместе с
  обрезанной строкой-цитатой, но без идентификатора источника, версии документа,
  координат и confidence.
- `_apply_contract_financial_terms` сразу заполнял пустые поля `Contract`.
- Несколько разных значений одного реквизита не распознавались как конфликт:
  использовалось первое совпадение.
- Производный аванс (процент от цены) получал тот же уровень доверия, что и явно
  указанная сумма.
- При конфликте существующей суммы остальные пустые поля могли быть заполнены
  частично.
- Существующий v5.4 `Evidence` уже поддерживает immutable source/version binding,
  locator, extractor и confidence. `EvidenceAssessment` отдельно хранит human
  verification. Создание второго evidence registry не требуется.
- `SourceVersion.legacy_document_version_id` является готовой точкой точного
  связывания с `DocumentVersion`, но текущие старые Drive-записи могут её не иметь.

## Реализовано

- Добавлен локальный parser `app.contract_evidence` без provider I/O и AI.
- Извлекаются:
  - цена договора;
  - сумма и процент аванса;
  - процент удержания;
  - дата договора;
  - срок действия до даты;
  - стороны: заказчик и подрядчик/исполнитель/поставщик.
- Для каждого совпадения возвращается exact locator:
  `text_range + unicode_codepoint + start/end`, confidence и безопасный excerpt
  только в API-ответе.
- В БД excerpt и значение реквизита не копируются. `Evidence` хранит координаты,
  extractor, confidence и точные `source_id/source_version_id`.
- Evidence ID детерминирован; повторный анализ идемпотентен и не создаёт дубликат.
- `EvidenceAssessment` создаётся как `unverified`: подтверждение человеком остаётся
  отдельным действием существующего Evidence API.
- Сохранение разрешено только при единственной связи:
  `DocumentVersion → SourceVersion.legacy_document_version_id → SourceCurrent`.
- Source должен принадлежать тому же tenant/project, быть доступным, текущим,
  иметь policy pins и консистентность `revision_bound` либо `digest_observed`.
- Отсутствующая/неоднозначная связь переводит результат в
  `manual_review_required`; слабый fallback по имени, URL или external ID запрещён.
- Разные значения одного поля дают `*_conflict`, значение не выбирается.
- Производный аванс имеет confidence `0.94` и требует проверки.
- Любой low-confidence/conflict блокирует автоматическое изменение договора.
- Конфликт с уже сохранённым значением блокирует весь набор изменений, исключая
  частичное заполнение.
- `analyze_contract` извлекает финансовые реквизиты только из точного текущего
  `DocumentVersion`, а не из смеси summary/notes/версий.

## Lifecycle

1. Текущий `DocumentVersion` выбирается по `document.current_version`.
2. Parser формирует значения и exact text ranges в памяти.
3. Проверяется единственная текущая `SourceVersion`, явно связанная с этой
   `DocumentVersion`.
4. Immutable Evidence и unverified assessment создаются в транзакции вызывающего
   endpoint.
5. При низкой уверенности, конфликте либо отсутствии точной версии Contract не
   меняется; клиент получает reason codes и evidence для review.
6. Только готовый high-confidence набор с сохранённым exact evidence может
   заполнить пустые поля. Несовпадение с существующим значением всегда требует
   человека.

## Схема БД

Новая таблица и Alembic-миграция не нужны. Повторно используются:

- `v54_sources`;
- `v54_source_versions.legacy_document_version_id`;
- `v54_source_current`;
- `v54_evidence`;
- `v54_evidence_assessments`.

Для полного подключения Drive ingestion должен атомарно заполнять существующее
`legacy_document_version_id`. Слабую временную связь в `Contract.notes`, JSON или
AuditLog не добавляли.

## Оставшиеся ограничения

- Реальный OCR/Drive ingestion пока не гарантирует заполнение
  `SourceVersion.legacy_document_version_id`; такие документы безопасно требуют
  review и не меняют Contract.
- Не добавлен UI подтверждения каждого извлечённого реквизита; используется
  существующая модель `EvidenceAssessment`, интеграция экрана — следующий поток.
- Срок действия возвращается с evidence, но не записывается в `warranty_until`,
  потому что это разные юридические понятия и отдельного поля срока договора нет.
- Стороны возвращаются с evidence, но не подменяют `counterparty` автоматически:
  роль контрагента зависит от типа договорной цепочки.
- PostgreSQL concurrency для идемпотентного создания Evidence в этом локальном
  окружении не выполнялся. Уникальные ограничения модели остаются последней
  защитой, обязательна runtime-проверка после интеграции.
