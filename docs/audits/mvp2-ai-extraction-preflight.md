Дата: 2026-09-11 (разделы 9-11 добавлены 2026-09-12)

Read-only анализ по подтверждённому решению: **полная замена** pipeline
извлечения в `task_engine.py`/`response_engine.py`/`governance_engine.py`

**Обновление 2026-09-12** — по итогам разделов 0-8 приняты два решения из

- **Scope замены (развилка 1, п. 8)** — решено в пользу **всех девяти
  вызывающих мест** (п. 0), включая bulk-сканирование (Drive/Yandex/OCR),

- **Fallback (развилка 4, п. 8)** — решён **Вариант А**: regex остаётся в

  оператора (`needs_review` + explicit-текст "LLM недоступен, поле не
  извлечено"). Классификация причин отказа — из Варианта В (§4.1) —
  используется как основа реализации fallback-логики независимо от этого
  выбора.

Разделы 9-11 ниже добавлены по прямому запросу — три оставшихся открытых

## 0. Главная находка — реальный масштаб замены больше, чем кажется

Прежде чем отвечать на 5 вопросов задания: `create_tasks_from_files`,
`create_response_drafts`, `create_governance_items` (функции, которые
предстоит менять) — это **не специфичный для AI Secretary код**, а общие,
переиспользуемые движки document-анализа, вызываемые из **девяти** разных
мест продукта:

| Вызывающий код | Контекст | source_type |
|---|---|---|
| `app/api/ai_secretary.py::_analyze_confirmed_message` | AI Secretary — то, что явно в scope задания | `email`/`telegram`/`document` |
| `app/organizer.py:172-175` | MVP-1 Drive/Yandex safe-copy анализ (Storage adapters область) — потенциально **сотни файлов за один вызов** | `document_analysis` (default) |
| `app/ocr_batch.py:114-116` | Массовый re-OCR документов проекта | `ocr_reprocess` |
| `app/api/workspace.py:509-512` | MVP-1 Snapshots — анализ содержимого snapshot'а | `document_analysis` |
| `app/local_upload_staging.py:288-292` | Локальная загрузка файлов | `document_analysis` |
| `app/staging/gmail_a05.py:568-574` | Gmail-вложения (durable staging) | зависит от вызова |
| `app/api/contract_package.py:100` | Анализ пакета документов договора | `contract_application` |
| `app/api/management.py:295-296` | Протоколы совещаний | `meeting` |
| `app/api/organizations_contracts.py:627-628` | Анализ текста договора | `contract_analysis` |
| `app/api/telegram.py:413-419` | Telegram-вложения | `telegram` |

Все девять принимают один и тот же provider-neutral тип
(`StorageObject`/`DriveFile` с полем `content_text`) — интерфейс единый,
но **объём и профиль вызовов принципиально разный**: AI Secretary
обрабатывает одно сообщение за раз (интерактивно, пользователь ждёт ответ);
`organizer.py`/`api/workspace.py` могут вызвать `create_tasks_from_files`
с сотнями файлов из одного Drive-скана за один backend-request (см.
`MAX_FILES_PER_SCAN` в Storage adapters preflight).

**Это меняет сам вопрос.** Задание сформулировано как "заменить
regex-подход в этих трёх файлах" — технически да, но у этих трёх файлов
девять разных потребителей с разными требованиями к задержке/стоимости/
устойчивости к сбоям AI. Решение нужно принимать не только для сценария
"пользователь ждёт разбор одного письма", но и для сценария "фоновый job
разбирает Drive-папку на 300 файлов" — LLM-вызов на файл там означает до
300 внешних API-запросов за один organizer-скан, с соответствующей
стоимостью, задержкой и экспозицией к rate-limit'ам провайдера. Это не
довод "не делать", но обязательный пункт для явного решения перед кодом:
**заменяется ли поведение только для AI Secretary (например, через новую
отдельную функцию, которую вызывает только `_analyze_confirmed_message`),
или для всех девяти вызывающих мест одновременно (правка самих
`create_tasks_from_files`/`create_response_drafts`/`create_governance_items`)?**
Задание пользователя буквально называет эти три файла — если это осознанный
выбор "менять для всех", ниже это учтено; если нет — до реализации нужно
явное уточнение.

## 1. Все места regex-извлечения поручения/срока — точные файлы, функции, тесты

### 1.1. `task_engine.py` (236 строк) — поручение + срок

| Функция | Что делает |
|---|---|
| `OBLIGATION_RE` (module-level regex) | Детектирует предложения с глаголами долженствования (должен/обязан/необходимо/поручить/…) |
| `DATE_RE`, `DEADLINE_DATE_RE`, `MONTH_DATE_RE` | Три отдельных regex на разные форматы даты-дедлайна |
| `extract_explicit_due_date(sentence) -> date | None` | Возвращает срок **только** при явном дедлайн-маркере (`не позднее`/`до`/`к`/`срок:`) — намеренно игнорирует даты-ссылки на документы (комментарий в коде: раньше это создавало ложные просроченные задачи) |
| `_text_quality_review_reasons(text)` | Детектирует OCR-повреждённый текст (не относится к полю "поручение", но влияет на `confidence`) |
| `extract_task_candidates(text, limit=5) -> list[TaskCandidate]` | Главная точка входа: сплит на предложения → фильтр по `OBLIGATION_RE` → дедуп по digest → `due_date` → `confidence` (0.90 с датой / 0.82 без / ≤0.45 при OCR-артефактах) |
| `_default_assignee(db, project_id) -> User | None` | **Не извлечение** — эвристический default по роли участника проекта (owner→manager→…), не связан с текстом письма |
| `create_tasks_from_files(...)` | Оркестрирует: вызывает `extract_task_candidates` на каждый файл, дедуп по `(project_id, source_file_id, source_excerpt_hash)`, создаёт `Task` + `Obligation` |

**Тесты, требующие переписывания под новое поведение:**
- `tests/test_task_engine.py` — 8 тестов, прямые: `test_extracts_obligation_with_deadline`,
  `test_ignores_plain_descriptive_text`, `test_extracts_russian_month_deadline_in_current_year`,
  `test_normative_reference_date_is_not_used_as_deadline`,
  `test_federal_law_date_is_not_used_as_deadline`,
  `test_reference_date_does_not_override_relative_obligation_term`,
  `test_explicit_deadline_marker_remains_supported`, `test_limits_candidates_per_file`
  — все проверяют **конкретное regex-поведение** (например, "дата из ссылки
  на СНиП/федеральный закон не должна стать сроком") — это не тривиально
  перенести на LLM 1:1; либо LLM должен воспроизводить ту же логику через
  промпт (без гарантии), либо эти тесты нужно переформулировать в
  контракт "что LLM обязан/не обязан делать", не "какой конкретно regex
  сработал".
- Косвенные (используют `create_tasks_from_files` через другие входные
  точки, значит зависят от его итогового поведения): `test_task_fragment_review.py`,
  `test_task_text_quality.py`, `test_risk_mitigation_regression.py`,
  `test_mvp3_hardening.py`, `test_ocr_batch.py`, `test_gmail_project_validation.py`,
  `test_v54_mailbox_identity.py`, `test_v54_mailbox_identity_postgres.py`,
  `test_mvp2_message_workflow.py`.

### 1.4. "Сумма" — отдельно, не в этих трёх файлах

Извлечение суммы **сегодня не структурное** — единственное место,
`summary_engine.py::brief_summary()`, находит **предложение** с ключевыми
словами (`стоимость`/`сумма`/`ндс`) и кладёт его целиком в текст сводки
(не число, не отдельное поле). `summary_engine.py` не был назван в задании
как файл на замену — но если LLM должен извлекать "сумму" как одно из
четырёх полей, `summary_engine.py` тоже фактически в scope (либо остаётся,
и "сумма" появляется только в новом LLM-based task-извлечении, отдельно от
сводки — тоже развилка для явного решения).

## 2. Существующий AI-адаптер — можно переиспользовать инфраструктуру, нельзя переиспользовать схему как есть

`app/integrations/ai.py::GeminiAIAdapter` — provider-neutral обёртка над
`app/gemini_analysis.py`. Уже есть:

- `configured_ai_provider() -> GeminiAIAdapter` — единая точка получения
  адаптера (задел на смену провайдера без правки вызывающего кода —
  комментарий в коде: "Vertical Slice 1 intentionally keeps one
  implementation").
- `provider.health().ready` — health-check без выполнения запроса
  (проверяет наличие `GEMINI_API_KEY`).
- **Structured output уже реализован**: `_generation_config()` строит
  `responseMimeType: application/json` + `responseSchema` (JSON Schema,
  нативная поддержка Gemini) — то есть механизм "LLM обязан вернуть валидный
  JSON по схеме" уже есть и используется (`ANALYSIS_SCHEMA`,
  `MESSAGE_REPLY_SCHEMA`, `MAIL_COMPOSER_SCHEMA`).
- **Retry уже есть**: `app/core/external_retry.py::HEAVY_AI_RETRY` — 3
  попытки, экспоненциальный backoff с jitter, retry на 408/425/429/500/
  502/503/504 и сетевых ошибках/таймаутах.
- **System instruction уже требует evidence**: текущий `SYSTEM_INSTRUCTION`
  в `gemini_analysis.py` буквально написан в духе задания — "Каждый вывод
  в массивах формулируй как: вывод — основание: «короткая точная цитата»"
  и "Не считай обычное описание работ поручением без явного требования или
  срока" — эта же формулировка **уже** кодирует то самое различие, которое
  сегодня делает `OBLIGATION_RE` через regex. Это готовый прецедент
  промпт-инженерии, не начинать с нуля.
- **Уже есть похожая, но не идентичная схема**: `ANALYSIS_SCHEMA`
  (используется в `analyze_document_with_gemini`, вызывается сегодня не из
  AI Secretary, а из отдельного document-анализа) уже содержит поля
  `obligations`, `amounts`, `dates` — но как **плоские массивы строк**, без
  привязки конкретного значения к конкретной evidence-цитате и без
  per-item confidence, и без поля "ответственный" вообще. Для задания
  нужна новая или существенно расширенная схема (см. п. 5).

**Итог по вопросу 2**: механизм подключения (`GeminiAIAdapter`,
`configured_ai_provider`, retry, structured output, project AI-policy
gate — см. п. 4) **переиспользуется полностью, без изменений**. Новым
кодом будет: (а) новая функция в `gemini_analysis.py` (например,
`extract_task_fields_with_gemini`) с новой JSON-схемой (п. 5) и новым
промптом; (б) её вызов из `task_engine.py`/или новой функции, заменяющей
`extract_task_candidates`.

## 3. Как хранится evidence сегодня — единый паттерн на 5 моделях, LLM-версия должна его сохранить

Один и тот же паттерн — **не совпадение**, а согласованный design поперёк
всего продукта:

| Модель | Поле-цитата | Поле-хеш (дедуп) | Поле-уверенность |
|---|---|---|---|
| `Task` | `source_excerpt: Text` | `source_excerpt_hash: String(64)` | `confidence: Float` |
| `Obligation` | `source_excerpt: Text` | `source_hash: String(64)` | `confidence: Float` (подтверждено — `app/models/management.py:30`) |
| `Risk`/`Decision` (governance) | `source_excerpt` | `source_hash` | `confidence` |
| `ResponseDraft` | `source_excerpt` | `source_excerpt_hash` | `confidence` |

**Прямой ответ на "куда писать"**: новая LLM-версия должна заполнять эти
же самые колонки на этих же самых таблицах (`Task.source_excerpt`/
`source_excerpt_hash`/`confidence`, аналогично для `Obligation`/`Risk`/
`Decision`/`ResponseDraft`) — **не заводить отдельную таблицу "LLM
extraction results" или параллельный набор полей**. Ничего в схеме для
поручения/срока менять не нужно (кроме, возможно, самого способа
формирования `source_excerpt`, см. ниже). Единственные потенциально
новые колонки — под "ответственный"/"сумма" (см. п. 5.4), которых сегодня
структурно нет вообще ни на одной модели, не только regex-версии.

Везде `source_excerpt` — это **дословная подстрока исходного текста**
(в regex-версии — буквально `sentence`, предложение, найденное `re.search`
внутри самого текста). Дедупликация построена на хеше именно этой цитаты
(`hashlib.sha256(excerpt.casefold())`) — то есть **гарантия дедупа
опирается на то, что evidence — точная подстрока исходника**, не
перефразированный LLM-текст.

**Это ключевое ограничение для LLM-версии**: если LLM вернёт
перефразированное "основание" (что LLM склонны делать даже при прямом
запросе цитаты — не гарантирована дословность), то (а) нарушается
прозрачность ("основание" — не то же самое, что реально написано в
письме), и (б) ломается существующий дедуп-механизм (хеш от
перефразированного текста не совпадёт при повторном разборе того же
письма → могут появиться дубликаты `Task`/`Risk` с разными по тексту, но
по сути одинаковыми evidence-цитатами). Соответственно, дизайн ответа LLM
(п. 5) должен либо (а) требовать от LLM вернуть **точную подстроку**
(и валидировать это программно — `evidence in original_text`, отбрасывая
кандидата, если не совпало), либо (б) дедуп/хеш переносится на **другой
якорь** (например, на само нормализованное значение поля — "поручение:
текст", "срок: дата" — а не на evidence-цитату). Это архитектурное решение,
не выбираю здесь.

## 4. Fallback-стратегия при недоступности/ошибке/невалидном ответе LLM

### 4.0. Не просто "сбой" — есть постоянный, не-availability источник запрета на LLM

`app/ai_policy.py::ProjectAIPolicy` уже существует и проверяется явно
(`prepare_external_ai_text`, `ExternalAIBlocked`) в
`api/mail.py::assist_mail_draft`. Режим `local_only` — это не "AI сейчас
недоступен", это **постоянный запрет** для конкретного проекта (по
причинам конфиденциальности), не зависящий от того, работает ли Gemini
API. **Какой бы вариант fallback ниже ни был выбран, `local_only`-проекты
обязаны иметь рабочий non-LLM путь всегда, не как временный fallback на
случай сбоя, а как постоянный режим работы** — это уже действующий
контракт продукта (проверяется в существующем тесте на `assist_mail_draft`,
см. `test_mail_client_api.py`), который новое извлечение обязано уважать
так же.

### 4.1. Три предложенных варианта

**Вариант А — regex как резервный механизм для поручения/срока, ответственный/сумма — пусто + пометка.**

При сбое LLM (таймаут/HTTP-ошибка после retry/невалидный JSON/пустой
ответ) — `extract_task_candidates`/`extract_explicit_due_date` (сегодняшний
regex, **не удаляется из кодовой базы**, остаётся постоянным fallback-
путём) подхватывает именно поручение и срок — те два поля, которые он и
сегодня находит с приемлемым качеством (см. п. 1: 8 существующих тестов на
конкретные регрессии типа "дата из ссылки на закон — не срок", уже
проверенная логика). Ответственный/сумма — поля, которых regex-версия
**никогда не извлекала** (п. 1.1/1.4) — остаются пустыми с явным флагом
(например, `needs_review=True` + пометка в `description`/новом поле "LLM
недоступен, поля не извлечены").

Плюсы: не теряет то, что уже надёжно работает; асимметрия ровно там, где
она объективно есть (regex и сегодня не может в ответственного/сумму, LLM
может). Минусы: **regex-код должен жить бессрочно**, не как временный
переходный код — это прямо противоречит духу "полная замена pipeline",
если понимать "замену" как "старый код можно удалить". Нужно явно
зафиксировать: при выборе A `task_engine.py`'s regex-функции остаются в
кодовой базе навсегда (as fallback), не подлежат последующему удалению.

**Вариант Б — письмо целиком в очередь на ручную обработку, ничего не извлекается автоматически.**

При сбое LLM — `Task`/`ResponseDraft`/`Risk`/`Decision` не создаются
вообще; сообщение получает явный статус ("требует полностью ручной
обработки" — нужен **новый** статус, ни `ready`/`needs_context_confirmation`/
`in_progress`/`completed` из `MessageStatusUpdate` (`api/ai_secretary.py`)
под это не подходит буквально) и видно оператору как есть, без единой
автоматической подсказки.

Плюсы: максимально просто, ничего не смешивается, нет риска "тихо
неполного" результата (частично LLM, частично regex, частично пусто).
Минусы: полностью убирает **и то, что regex сегодня делает надёжно** (п.4
Вариант А сохраняет это, Б — нет) — заметная деградация полезности именно
в тот момент (сбой LLM), когда пользователю особенно важно, чтобы хоть
что-то было найдено автоматически. Для bulk-вызовов (`organizer.py` на
сотнях файлов, см. п. 0) — временный сбой LLM API означает "ни одной
задачи не создано" на весь скан, не только для одного письма.

**Вариант В — существующий в main паттерн (`assist_mail_draft`) как основа, с поправкой на то, что он не переносится 1:1**

Проверил точный код `assist_mail_draft` (`api/mail.py:332-379`) — там
действительно есть **готовая, уже проверенная тестами (`test_gemini_mail_assist_uses_policy_and_never_sends`)
таксономия ошибок**, ровно то, что нужно для "надёжного fallback":

```python
try:
    ai_text, policy_mode = prepare_external_ai_text(db, project_id, combined)
except ExternalAIBlocked as exc:
    raise HTTPException(409, "external_ai_blocked_by_project_policy") from exc
provider = configured_ai_provider()
if not provider.health().ready:
    raise HTTPException(503, "ai_provider_not_configured")
try:
    result = provider.compose_message(...)
except Exception as exc:
    raise HTTPException(502, "ai_provider_temporarily_unavailable") from exc
...
if not body:
    raise HTTPException(502, "ai_provider_returned_empty_draft")
```

Четыре **явно различённых** причины отказа: project-policy блокировка
(409), провайдер не настроен (503), временный сбой при самом вызове (502),
невалидный/пустой ответ (502, отдельная причина). Эта классификация **прямо
переиспользуема** для task-извлечения — те же четыре причины актуальны один
в один.

**Но то, что происходит ПОСЛЕ классификации ошибки, переносится не 1:1.**
`assist_mail_draft` — интерактивная, **опциональная** пользовательская
команда (кнопка "помочь с письмом"): на любой из четырёх ошибок он просто
прерывается HTTP-ответом с ошибкой, ничего не создавая — и это нормально,
потому что весь остальной mail-flow (существующие черновики, ручное
составление, отправка уже одобренного) не завязан на эту кнопку и
продолжает работать. Task/поручение-извлечение — **не опциональная
команда**, а обязательный шаг внутри `_analyze_confirmed_message`,
вызываемого автоматически при подтверждении сообщения (и, для bulk-
вызовов, при каждом file в скане, п. 0) — оборвать всю обработку
сообщения `raise`'ом на любой из этих четырёх ошибок means "письмо/файл
целиком не обработан", что и есть по сути Вариант Б, только через
исключение, а не через явный статус.

**Итог по В**: сама **классификация** ошибок (4 явные причины,
`assist_mail_draft`'s таксономия) стоит переиспользовать буквально, вне
зависимости от того, какой из вариантов А/Б выбран как *реакция* на неё —
это готовый, протестированный словарь причин отказа. Но "что делать
дальше" — это снова выбор между А (regex-fallback на 2 из 4 полей) и Б
(явный статус "не обработано"), эта часть не решается копированием
`assist_mail_draft`, потому что у него принципиально другой caller
(опциональная кнопка vs обязательный шаг pipeline).

Ни один из А/Б не выбираю — как и просили. Классификация ошибок из В
рекомендую как основу независимо от выбора А/Б (это не альтернатива им, а
слой ниже — "как понять, что случилось", а не "что делать, когда
случилось").

## 5. Дизайн формата ответа LLM (structured output) — предложение

Опираясь на существующий паттерн (`ANALYSIS_SCHEMA`/`MESSAGE_REPLY_SCHEMA`
в `gemini_analysis.py`, native `responseSchema` Gemini) и на evidence-
паттерн из п. 3 (дословная цитата + confidence на каждую единицу, не на
весь ответ разом — сегодняшний `TaskCandidate`/`Obligation` несут
confidence **на кандидата**, не общий на всё сообщение):

```python
TASK_FIELD_EXTRACTION_SCHEMA = {
    "type": "object",
    "properties": {
        "obligations": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "title": {"type": "string"},          # краткая формулировка поручения
                    "evidence_quote": {"type": "string"},  # ДОСЛОВНАЯ подстрока исходного текста
                    "due_date": {"type": ["string", "null"]},       # ISO 8601 или null
                    "due_date_evidence_quote": {"type": ["string", "null"]},  # отдельная цитата под срок — может не совпадать с цитатой под поручение
                    "assignee_hint": {"type": ["string", "null"]},  # ИМЯ/должность из текста, НЕ user_id — сопоставление с реальным User остаётся на стороне приложения
                    "assignee_evidence_quote": {"type": ["string", "null"]},
                    "amount": {"type": ["number", "null"]},
                    "amount_currency": {"type": ["string", "null"]},
                    "amount_evidence_quote": {"type": ["string", "null"]},
                    "confidence": {"type": "string", "enum": ["low", "medium", "high"]},
                },
                "required": [
                    "title", "evidence_quote", "due_date", "due_date_evidence_quote",
                    "assignee_hint", "assignee_evidence_quote",
                    "amount", "amount_currency", "amount_evidence_quote", "confidence",
                ],
            },
        },
    },
    "required": ["obligations"],
}
```

Ключевые проектные решения этого черновика (каждое — тоже развилка, не
финал):

1. **Отдельная evidence-цитата на каждое под-поле**, не одна на весь
   "obligation". В реальном письме поручение, срок и ответственный часто
   находятся в разных предложениях ("Прошу подготовить отчёт. Ответственный
   — Петров. Срок — до 20.09.") — единая цитата на всё потеряла бы
   прозрачность именно там, где источники расходятся.
2. **`confidence` как enum `low/medium/high`**, не float — сознательно
   ближе к существующему `ANALYSIS_SCHEMA`/`MESSAGE_REPLY_SCHEMA` (тот же
   enum уже используется), а не к сегодняшнему float в `Task.confidence`.
   Маппинг enum→float (для сохранения в БД как есть) — отдельное явное
   решение (low=0.45? high=0.90? нужно сверить с текущими порогами
   `context_confirmed = confidence >= 0.90`, чтобы не разъехаться по
   семантике).
3. **`assignee_hint` — текстовая подсказка, не `user_id` напрямую.** LLM
   не должен и не может достоверно знать внутренние ID пользователей
   проекта; сопоставление "Петров" → `ProjectMember.user_id` — отдельная,
   детерминированная (не-LLM) логика на стороне приложения (по аналогии с
   сегодняшним `_default_assignee`, но с реальным кандидатом на сопоставление,
   не голым fallback по роли). Если сопоставление не найдено — вероятно,
   `needs_review=True` и `assignee_user_id` остаётся на прежнем
   role-based fallback, с `assignee_hint` сохранённым отдельно для
   отображения пользователю ("LLM предположил: Петров — не найден среди
   участников проекта").
4. **`amount`/`amount_currency` как отдельные структурные поля** — на
   `Task`/`Obligation` сегодня таких колонок нет (см. п. 1.4) — потребуется
   новая миграция схемы, если поле должно быть структурным, а не только
   частью текста сводки. Это выходит за рамки "не пишу код" в объёме
   анализа, но стоит зафиксировать явно как обнаруженное требование:
   **эта фича не помещается в текущую схему БД без добавления колонок**.
5. **Постобработка обязательна, LLM-вывод не идёт в БД напрямую.**
   Минимум: (а) валидация `evidence_quote in original_text` (см. п. 3) —
   отбрасывать/понижать confidence для полей, где LLM не смог процитировать
   дословно; (б) валидация `due_date` как реального ISO-парсинга, а не
   доверие к тому, что LLM написал валидную дату; (в) sanitize/length-limit
   на все строковые поля (сегодняшние модели имеют `String(500)`/`Text`
   ограничения — LLM не знает о них).

## 9. Rate-limiting/батчинг для bulk-сценариев

### 9.0. Масштаб проблемы — конкретные числа из кода, не предположение

`MAX_FILES_PER_SCAN = 2000` (`organizer_engine/config.py:22`, задаётся
через `os.getenv`, дефолт 2000) — один Drive/Yandex-скан может дать до
2000 `StorageObject`. Сегодня `organizer.py:172-175` вызывает три функции
последовательно на этом же списке файлов:

```python
tasks = create_tasks_from_files(db, project_id, session_id, copy_items)
drafts = create_response_drafts(db, project_id, session_id, copy_items)
risks, decisions = create_governance_items(db, project_id, copy_items)
```

Если каждая из трёх функций делает по одному LLM-вызову на файл (см. §8
развилку 7) — это до **6000 LLM-вызовов за один скан**. Даже при
комбинированном вызове (один вызов на файл, развилка 7) — до **2000**.
Оба числа считать надо от `MAX_FILES_PER_SCAN`, не от типичного случая:
лимит существует именно потому, что скан на несколько сотен-тысяч файлов —
предусмотренный, не крайний сценарий (тот же лимит используется в
`walk_tree`/`copy_folder_tree` как жёсткая граница, скан выше него **не
стартует** — `organizer_engine/drive.py:311-315`).

Сегодняшний цикл — `for file in files: ...` в `task_engine.py:188` —
строго последовательный, синхронный `httpx.Client` (`gemini_analysis.py`,
`timeout=90.0`). Один вызов LLM на файл при последовательном исполнении **не
рискует превысить RPM** сам по себе (следующий вызов стартует только после
ответа на предыдущий) — но упирается в **RPD** (запросов в сутки) и в общее
время выполнения (см. §10), а на дешёвых/бесплатных тарифах Gemini — и в
RPM тоже, если фактическая задержка одного вызова короче, чем `60/RPM`
секунд.

Ориентиры по тарифам Gemini API (открытые источники, сентябрь 2026 — не
проверено на реальном ключе этого проекта, см. §7):
- **Free**: 10 RPM, ~250 000 TPM, 500 RPD для Flash-уровня.
- **Tier 1** (после включения биллинга, без минимального платежа):
  300 RPM, ~1 000 000 TPM, 1 000 RPD.
- Tier 2/3 — выше, но требуют кумулятивных прошлых платежей ($250/$1000).
([tinkerllm.com](https://tinkerllm.com/blog/gemini-api-free-tier-limits-rate-quotas/),
[aipromptshub.co](https://aipromptshub.co/limits/gemini-rate-limits-2026))
Точные цифры именно для `gemini-3.6-flash` (текущая модель проекта,
`GEMINI_MODEL` env, `gemini_analysis.py:99`) нужно свериться в консоли
Google AI Studio/Cloud для реального ключа — приведённые числа относятся к
Flash-уровню в целом и могут отличаться посимвольно для конкретной версии
модели.

На **Free**-тарифе даже 500 RPD исчерпываются один разом на скане из
~166 файлов (при 3 вызовах/файл) или ~500 файлов (при 1 вызове/файл) —
то есть дефолтный `MAX_FILES_PER_SCAN=2000` **гарантированно** упрётся в
дневную квоту на Free-тарифе независимо от выбранной ниже стратегии
батчинга. Это не вопрос архитектуры вызова, а вопрос тарифного плана,
который нужно решить отдельно (переход на Tier 1+ обязателен для bulk-
сценариев в проде, если вообще держать `MAX_FILES_PER_SCAN` в текущем
значении).

### 9.1. Варианты (ни один не выбран)

**Вариант А — оставить последовательным (без изменений в способе вызова).**

Просто заменяет тело текущего `for`-цикла на LLM-вызов вместо regex,
структура кода не меняется. Естественно не превышает RPM (сам ограничен
собственной задержкой), прост в реализации и в диагностике сбоев (один
вызов — одна ошибка, без гонки состояний). Минус — время скана растёт
линейно с числом файлов и с задержкой одного вызова (см. §10: секунды на
файл × тысячи файлов = десятки минут — час на один скан), полностью
съедая любые преимущества от предыдущей regex-скорости (миллисекунды на
файл). Не решает проблему RPD на Free-тарифе (см. 9.0) — только не
усугубляет её сверх последовательного темпа.

**Вариант Б — ограниченный пул воркеров (bounded concurrency).**

`asyncio.Semaphore`/`ThreadPoolExecutor` с фиксированным числом
одновременных LLM-вызовов N, подобранным под фактический RPM-тариф
проекта (например, N=5 при Tier 1's 300 RPM с вызовом ~2-6 c — не
превышает лимит, но и не использует его полностью; N нужно тюнить под
измеренную, не предполагаемую, задержку). Сокращает время скана
приблизительно в N раз против Варианта А. Требует: (а) перевода
последовательного `for`-цикла в `task_engine.py`/`response_engine.py`/
`governance_engine.py` на конкурентное исполнение — не тривиальная правка,
если остальной код синхронный (SQLAlchemy `Session` не потокобезопасна
между воркерами без отдельной сессии на воркер); (б) явной обработки
частичных сбоев — часть файлов в пуле может завершиться ошибкой, пока
другие успешны, нужна агрегация по каждому файлу независимо (сочетается с
Fallback Вариантом А из §4, применённым **на уровне отдельного файла**, не
всего скана).

**Вариант В — provider-side batch API.**

Пороговая пометка тарифов Gemini выше ($0.375/$1.875 за млн токенов
"Batch/Flex" против $0.75/$3.75 "Standard" — см. §10) намекает на
существование отдельного асинхронного batch-режима у Google (submit-and-
poll, а не синхронный HTTP-запрос на файл). Даёт лучшую цену **и**,
предположительно, отдельную от live-RPM квоту (типично для batch API
других провайдеров) — но: (а) не проверено, поддерживает ли текущий
`app.integrations.ai.GeminiAIAdapter`/REST-эндпоинт (`generateContent`)
batch-режим вообще, требует отдельного исследования API Google
(`app/gemini_analysis.py` сегодня зовёт только `:generateContent`, не
batch-эндпоинт); (б) типичный SLA batch-API у LLM-провайдеров — часы, не
секунды/минуты — превращает "асинхронный job с прогресс-баром" (§11) в
"асинхронный job с ожиданием часы", что для интерактивного сценария (один
файл в AI Secretary) избыточно, но может подойти для `organizer.py`'s
overnight-сканов на тысячи файлов, если бизнес-процесс это допускает
(сегодня скан ожидается пользователем в течение сессии, судя по прогресс-
бару в `OrganizerRepository.update_session`).

**Вариант Г — regex как предфильтр перед LLM-вызовом (сокращение числа вызовов, не задержки одного вызова).**

Оставляет старые `OBLIGATION_RE`/`REQUEST_RE`/`RISK_RE`/`DECISION_RE` в
коде, но меняет их роль: не извлекать поле, а **решать, стоит ли вообще
звать LLM** для этого файла (например, файл без единого совпадения по
всем regex-детекторам с высокой вероятностью не содержит ни поручения, ни
запроса, ни риска — пропускается без LLM-вызова вовсе). Сокращает число
LLM-вызовов на скан (не факт, что кардинально — зависит от доли "пустых"
файлов в реальных Drive-папках, не измерено). Явное следствие: **regex
возвращается в pipeline не как fallback (§4), а как постоянный
предфильтр** — то есть даже при выбранном Fallback Варианте А (§4, где
regex — только резерв на случай сбоя LLM) появляется второе,
самостоятельное основание держать regex-код активным и поддерживаемым
навсегда, не просто "на случай сбоя". Стоит явно решить, накладывается ли
этот вариант поверх Б/В или это отдельная, самодостаточная мера (можно
взять только Г, не трогая параллелизм — уменьшить количество вызовов,
оставив их последовательными).

Варианты не взаимоисключающие — например, Б+Г (пул воркеров + regex-
предфильтр) или В+Г для по-настоящему больших сканов. Ни один не выбираю.

## 10. Оценка стоимости и времени на 100/500/1000 файлов

**Оговорка перед цифрами**: ничего ниже не измерено прогоном на реальном
API-ключе этого проекта — это модельный расчёт на основе (а) официальной
страницы цен Google AI (через `ai.google.dev/gemini-api/docs/pricing`,
проверено 2026-09-12) и (б) структуры существующего кода
(`text[:50_000]`-обрезка промпта в `gemini_analysis.py:102`, отсутствие
обрезки где-либо ещё). Перед тем как фиксировать бюджет/SLA — нужен
реальный замер на нескольких типичных письмах/документах проекта.

### 10.1. Стоимость (per-call, затем × число файлов × число вызовов/файл)

Цена `gemini-3.6-flash` (Standard, действует до 2026-12-31):
**$0.75 / млн input-токенов, $3.75 / млн output-токенов**
([chatbase.co](https://www.chatbase.co/blog/gemini-3-6-flash),
[ai.google.dev](https://ai.google.dev/gemini-api/docs/pricing) — Free-тир
существует, но недостаточен для bulk, см. §9.0). С 2027-01-01 цена растёт
до $1.50/$7.50 — если проект будет ещё работать с этой моделью в проде
после этой даты, бюджет ниже нужно удвоить.

Промпт сегодня обрезается до **50 000 символов** перед отправкой
(`text[:50_000]`, `gemini_analysis.py:102`, уже используется в
`analyze_document_with_gemini` — прямой прецедент для новой функции
извлечения). При грубой оценке ~4 символа/токен для смешанного
русский/английский текста — это **до ~12 500 токенов input** на файл в
худшем случае (файл, реально длиннее лимита обрезки); плюс system
instruction + JSON-схема (`ANALYSIS_SCHEMA`-подобная, §5) — ещё
приблизительно 500-1000 токенов постоянных накладных расходов на вызов.
Типичное короткое письмо/документ (не обрезанное лимитом) — на порядок
меньше, ориентировочно 300-3000 токенов input.

| Сценарий на 1 вызов | Input (токены) | Output (токены, JSON-схема) | Цена/вызов |
|---|---|---|---|
| Типичное короткое письмо | ~2 000 | ~400 | ~$0.0030 |
| Обрезанный лимитом документ (50 000 симв.) | ~13 500 | ~800 | ~$0.0132 |

| Файлов | 1 вызов/файл (комбинированная схема, §8 развилка 7), типичный сценарий | то же, худший (все обрезаны лимитом) | 3 вызова/файл (сегодняшняя структура из 3 функций), типичный | то же, худший |
|---|---|---|---|---|
| 100 | ~$0.30 | ~$1.32 | ~$0.90 | ~$3.96 |
| 500 | ~$1.50 | ~$6.60 | ~$4.50 | ~$19.80 |
| 1000 | ~$3.00 | ~$13.20 | ~$9.00 | ~$39.60 |

Даже в худшем варианте (3 вызова/файл, все документы у лимита обрезки) —
абсолютная сумма для 1000 файлов (~$40) сама по себе не выглядит
блокирующей. **Развилка не про доллары, а про RPD/RPM (§9.0)** — на
Free-тарифе скан такого размера физически не пройдёт по квоте запросов
задолго до того, как стоимость станет проблемой; на оплаченном тарифе
доллары — не аргумент против, время (ниже) и лимит запросов — аргумент.

### 10.2. Время выполнения

Задержка одного вызова `gemini-3.6-flash` с включённым `thinkingLevel: low`
(уже задано в `_generation_config` для моделей `gemini-3*`,
`gemini_analysis.py:86-87`) и structured output — не измерена на этом
проекте; для Flash-уровня в целом типичный порядок величины для короткого
промпта со structured-output — единицы секунд (не десятки), но это нужно
подтвердить реальным замером, а не полагаться на этот текст. При
`timeout=90.0` (`gemini_analysis.py`) и `HEAVY_AI_RETRY`
(`attempts=3, base_delay=1.0, max_delay=12.0`,
`core/external_retry.py:25`) — единичный сбойный вызов с retry может
занять до `90×3 + backoff` секунд в пессимистичном случае (провайдер
не отвечает на все три попытки), это не типичный, а граничный случай.

Ниже — **последовательное** исполнение (Вариант А из §9.1, без пула
воркеров), при двух предположениях о типичной задержке одного успешного
вызова (2 с и 5 с — диапазон, не измерение):

| Файлов | 1 вызов/файл, 2 с/вызов | 1 вызов/файл, 5 с/вызов | 3 вызова/файл, 2 с/вызов | 3 вызова/файл, 5 с/вызов |
|---|---|---|---|---|
| 100 | ~3.3 мин | ~8.3 мин | ~10 мин | ~25 мин |
| 500 | ~17 мин | ~42 мин | ~50 мин | ~2.1 ч |
| 1000 | ~33 мин | ~83 мин | ~1.7 ч | ~4.2 ч |

Для сравнения: сегодняшний regex-путь на том же объёме — миллисекунды на
файл, весь скан на 1000 файлов укладывается в секунды сверх времени самого
Drive-копирования/OCR. **Это и есть количественное обоснование §11** —
рост на два-три порядка по времени одной операции `create_tasks_from_files`
и аналогов при последовательном LLM-вызове несовместим с тем, что часть
вызывающих мест сегодня синхронны в HTTP-запросе (обычный HTTP-таймаут
клиента/прокси — секунды-десятки секунд, не часы). Пул воркеров (§9.1,
Вариант Б) делит эти цифры на N, но не убирает порядок величины роста
против сегодняшнего regex.

## 11. Confirmation UX — синхронный vs асинхронный флоу с прогресс-баром

### 11.0. Не все девять вызывающих мест — в одном и том же положении сегодня

Проверил построчно: часть вызывающих мест из §0 **уже** асинхронны
(идут через `app/jobs/queue.py::enqueue`, отдают `job_id`/`status` сразу и
опрашиваются отдельным GET-эндпоинтом с полем `progress`), часть —
**синхронны**, выполняются целиком внутри одного HTTP-запроса:

| Вызывающий код | Сегодня | Механизм |
|---|---|---|
| `organizer.py` (`/organizer/scan`) | **Async, с прогрессом** | `enqueue(db, "organizer.scan", ...)` → `{"status": "queued", "job_id": ...}`; `GET /organizer/sessions/{id}` возвращает `progress` (0-100, обновляется по ходу скана, `OrganizerRepository.update_session`) |
| `api/workspace.py` (`/snapshots/{id}/analyze`) | **Async** | `enqueue(db, "workspace.analysis", ...)` → `{"status": "analyzing"}`; повторный вызов возвращает `{"already_queued": True}` |
| `ocr_batch.py` (`reprocess_documents`) | **Async, с прогрессом** | вызывается как job-функция с `job_id`, использует `update_cooperative_progress` (`app/jobs/queue.py`) |
| `local_upload_staging.py` | **Async** | использует `enqueue`/`current_execution_claim` из `app/jobs/queue.py` |
| `api/ai_secretary.py` (`confirm_context`, `confirm_context_bulk`) | **Sync, в запросе** | `_analyze_confirmed_message(db, row)` вызывается напрямую в теле POST-обработчика; `confirm_context_bulk` — цикл по **нескольким** сообщениям в одном запросе |
| `api/contract_package.py` (`analyze_contract_package`) | **Sync, в запросе** | цикл по прикреплённым к договору документам (обычно единицы-десятки, не сотни) внутри одного POST |
| `api/organizations_contracts.py` | **Sync, в запросе** | один вызов на текст договора |
| `api/management.py` | **Sync, в запросе** | один вызов на протокол совещания |
| `api/telegram.py` (`webhook`) | **Sync, в запросе** (`async def`, но LLM-вызов внутри того же обработчика) | один вызов на вложение, real-time ответ боту |

Это меняет формулировку вопроса из задания. Для четырёх уже-асинхронных
путей (Drive/Yandex-скан, snapshot-анализ, OCR-batch, local-upload) —
задача не "переводить синхронный флоу в асинхронный" (он уже асинхронный),
а "продлить существующий progress-репортинг на фазу LLM-извлечения",
которая сегодня выполняется одним куском в конце скана (`progress=95` →
тасков/драфтов/рисков создание → `progress=100`, без промежуточных
отметок внутри самого `create_tasks_from_files`/аналогов, см.
`organizer.py:169-176`). Реальный открытый вопрос — про **пять**
оставшихся синхронных мест, из которых по-настоящему "bulk-shaped"
(несколько единиц обработки за один HTTP-запрос) — `confirm_context_bulk`
(несколько сообщений) и `analyze_contract_package` (несколько документов);
остальные три обрабатывают один файл/письмо за вызов, и рост с
миллисекунд до единиц секунд (§10.2) для них, вероятно, всё ещё приемлем
для синхронного HTTP-ответа — но это тоже развилка ниже, не факт.

### 11.1. Варианты (ни один не выбран)

**Вариант А — оставить синхронным, принять рост задержки ответа.**

Не меняет форму API/фронтенда вообще. Для одиночных вызовов (§10.2: ~2-5 с
на файл при 1 вызове/файле) — рост заметный, но, вероятно, терпимый для
интерактивного действия вроде "подтвердить контекст письма" (пользователь
и так ждёт результата, как при существующем `assist_mail_draft`, у
которого нет прогресс-бара и это принято сегодня). Для `confirm_context_bulk`
и `analyze_contract_package` с несколькими элементами за раз — задержка
складывается (N × 2-5 с), и уже может упереться в таймаут HTTP-клиента
(браузер/прокси/API-gateway) при достаточно большом N. Минус: без
изменений сама реализация проще всего, но именно два bulk-shaped
эндпоинта рискуют стать нестабильными по мере роста N (сколько сообщений
пользователь реально подтверждает одним `confirm_context_bulk`-вызовом —
не измерено, зависит от использования продукта).

**Вариант Б — перевести только два bulk-shaped синхронных места на
async+progress (`confirm_context_bulk`, `analyze_contract_package`),
остальные три (`management.py`, `organizations_contracts.py`,
`telegram.py`) оставить синхронными как обрабатывающие один файл за
вызов.**

Переиспользует уже существующий паттерн `app/jobs/queue.py` (`enqueue` +
polling-эндпоинт с `progress`), а не изобретает новый — тот же механизм,
что уже несёт `organizer.py`/`workspace.py`/`ocr_batch.py`. Минимизирует
объём фронтенд-изменений (прогресс-бар нужен только там, где счёт вызовов
реально может быть большим). Минус: требует явно провести границу
"сколько элементов — уже bulk, а сколько — ещё одиночный вызов" (например,
`confirm_context_bulk` на 2 сообщениях vs на 50 — качественно разная
задержка, порог для перевода в async нужно зафиксировать явно, а не
"всегда/никогда").

**Вариант В — перевести все девять/пять оставшихся мест на единый
async+progress паттерн без исключений, независимо от типичного размера
пакета.**

Максимально единообразно — один паттерн ("подтвердил действие → получил
job_id → опрашиваешь прогресс") на весь продукт, включая telegram-webhook
и одиночные письма/протоколы совещаний, даже там, где сегодня задержка,
вероятно, останется в пределах 2-5 секунд. Плюс: не нужно заново решать
этот вопрос при следующем изменении объёма ("а что если 5 писем в
telegram за раз в будущем понадобится?"). Минус: `telegram.py::webhook` —
это ответ боту в реальном времени в рамках уже входящего вебхука от
Telegram; перевод на async job означает, что первичный ответ пользователю
в мессенджере должен стать "принято, обрабатываю" с последующим отдельным
сообщением о результате — изменение UX-контракта бота, не только backend-
рефакторинг. Больше объём работы, чем Вариант Б, для выгоды, которая
сегодня не обязательно материализуется (одиночные вызовы, вероятно, и так
укладываются в секунды).

Ни один вариант не выбираю. Промежуточное наблюдение независимо от
выбора: если Вариант Б или В выбраны, для уже-асинхронных четырёх мест
(организатор/snapshot/OCR/local-upload) минимальная доработка всё равно
нужна — продлить `update_session`/`update_cooperative_progress`-репортинг
внутрь `create_tasks_from_files` и аналогов (по файлу, а не одним куском в
конце), иначе пользователь увидит "завис на 95%" на весь LLM-этап скана.
