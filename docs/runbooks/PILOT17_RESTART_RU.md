# Повторный тест AUTO проекта 17 — пять суток

Отсчёт начинается при фактическом выпуске новой policy после прохождения
preflight, а не при подготовке исправления. Владелец — user_id=1.

## Telegram

- Обновить именно telegram-relay: обновление backend/worker не обновляет
  отдельный контейнер relay автоматически.
- Проверить `/health`: свежий `last_poll_at`, `status=healthy`, отсутствие
  `last_error`. При старте без успешного polling и после 90 секунд без
  успешного цикла health должен быть degraded.
- Сопоставить `errors_total`, `last_error_operation`, `last_error_status`,
  `recoveries_total` с логами контейнера. История health ограничена текущим
  процессом; перезапуск не является доказательством отсутствия инцидентов.
- Проверить getMe/getChat только чтением. Проверка не подтверждает доставку
  сообщения. Для реальной отправки тестового оповещения требуется отдельное
  разрешение, если запрет тестовых сообщений не отменён владельцем.
- `outbound` отдельно показывает подтверждённые отправки и ошибки отправки.
  Не повторять sendMessage после сетевого сбоя: результат может быть UNKNOWN.
  Ошибки чтения/502 getUpdates нельзя исправить обещанием непрерывной связи.

## Кандидат

Нужно реально полученное Gmail-письмо с явно помеченным тестовым заданием,
однозначным номером договора проекта 17 и конкретным будущим сроком.
Нельзя подменять provider_message_id, source provenance, confidence,
context confirmation или audit прямым UPDATE/фикстурой в production.

Пример текста для согласования с владельцем (не отправлять автоматически):

> [TEST AUTO P17] По договору <точный номер договора проекта 17>:
> подготовить внутреннюю тестовую заметку. Срок: <дата внутри нового окна>.
> Это тест; внешняя публикация не требуется.

После штатного импорта проверить: project_id=17, contract_id относится к 17,
confidence >=0.9, настоящие mailbox/source refs; ровно одна task-кандидат
со сроком, confidence >=0.9 и единственной точной цитатой в письме.
Отдельное явное подтверждение владельцем выполняется штатным
confirm-context-for-auto. Обычное подтверждение проекта этого не заменяет.
Пустой набор кандидатов — тест не готов, а не успешный нулевой тест.

## Запуск и приёмка

1. Повторить read-only incident gate по jobs, receipts, quotas, rollback,
   integrity/CAS и readiness. При неизвестном результате запуск запрещён.
2. Зафиксировать начало и конец (+5 суток). Через versioned/CAS сервис
   обновить authority строго project=17/user=1 с прежними permissions,
   затем policy с прежними квотами/порогом и TTL не более 24 часов.
   Внешние сообщения остаются CONFIRM, mailbox actions/primary_read выключены.
3. После подтверждения конкретного письма проверить producer job, ProductIntent,
   dispatch, APPLIED receipt с SERVER_POLICY и фактическую внутреннюю задачу.
4. Проверить отдельно APPLIED receipt внутреннего notification. Task-success
   не является доказательством notification-success; отсутствие producer для
   соответствующего события фиксировать как пробел, не фабриковать intent.
5. Только после подтверждённой приёмки возобновлять наблюдение по согласованным
   правилам. Продления прекращаются при инциденте и по концу окна; никогда
   не использовать authority.manage для обхода gate.

Изолированные regression-тесты подтверждают код, но не заменяют live-приёмку.
Старые policy revision 4 / authority epoch 2 не изменять до нового чистого gate.
